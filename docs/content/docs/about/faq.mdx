## Can I use flexiq with Django?

Yes. Create a `Queue` instance in one of your Django apps and import it where needed:

```python
# myproject/tasks.py
from flexiq import Queue

queue = Queue(db_path="flexiq.db")

@queue.task()
def send_welcome_email(user_id: int):
    from myapp.models import User
    user = User.objects.get(id=user_id)
    user.email_user("Welcome!", "Thanks for signing up.")
```

Import tasks lazily inside the function body to avoid Django app registry
issues. Start the worker separately:

```bash
DJANGO_SETTINGS_MODULE=myproject.settings flexiq worker --app myproject.tasks:queue
```

## Can I use flexiq with Flask?

Yes. Same pattern — define a queue, decorate tasks, run the worker:

```python
# tasks.py
from flexiq import Queue

queue = Queue(db_path="flexiq.db")

@queue.task()
def generate_report(report_id: int):
    from myapp import create_app
    app = create_app()
    with app.app_context():
        ...
```

</SdkOnly>

## Can I use flexiq with Express, Fastify, or NestJS?

Yes — all three. Define the queue and tasks once, then mount the REST API and
dashboard with the matching contrib helper. The worker runs the same way
regardless of framework; each helper's peer (`express` / `fastify` /
`@nestjs/common`) is installed separately.

**Express** — `@byteveda/flexiq/contrib/express`:

```ts
import express from "express";
import { flexiqRouter, flexiqDashboard } from "@byteveda/flexiq/contrib/express";

const app = express();
app.use("/tasks", flexiqRouter(queue));     // REST API
app.use("/admin", flexiqDashboard(queue));  // dashboard SPA
app.listen(3000);
```

**Fastify** — `@byteveda/flexiq/contrib/fastify`:

```ts
import Fastify from "fastify";
import { flexiqFastify, flexiqDashboardPlugin } from "@byteveda/flexiq/contrib/fastify";

const app = Fastify();
await app.register(flexiqFastify, { queue, prefix: "/tasks" });
await app.register(flexiqDashboardPlugin, { queue, prefix: "/admin" });
await app.listen({ port: 3000 });
```

**NestJS** — `@byteveda/flexiq/contrib/nest`:

```ts
import { Module } from "@nestjs/common";
import { FlexiQModule } from "@byteveda/flexiq/contrib/nest";

@Module({ imports: [FlexiQModule.forRoot(queue)] })
export class AppModule {}
```

Inject `FlexiQService` into your providers to enqueue and read results.

</SdkOnly>

## Can I use flexiq with Spring Boot?

Yes, via the `org.byteveda:flexiq-spring` starter (Spring Boot 3). Add it and
the auto-configuration builds a `FlexiQ` bean from your `flexiq.*` properties
— inject it anywhere:

```java
@Service
public class SignupService {
    private final FlexiQ flexiq;
    public SignupService(FlexiQ flexiq) { this.flexiq = flexiq; }

    public void register(User user) {
        flexiq.enqueue("send_welcome_email", user.email());
    }
}
```

```yaml
flexiq:
  url: postgres://localhost/flexiq
  pool-size: 8
  namespace: my-app
```

The worker is not auto-started — build one from the injected bean in an
`ApplicationRunner`, or set `flexiq.dashboard.enabled=true` to auto-start the
dashboard. Non-Spring apps just build a `FlexiQ` and `Worker` programmatically.

</SdkOnly>

## Can multiple processes share the same SQLite file?

Yes, with caveats. SQLite in WAL mode allows concurrent readers and one writer
at a time. flexiq sets `busy_timeout=5000ms` to handle contention.

However, flexiq is designed as a **single-process** task queue. Multiple
worker processes against one database works but will see diminishing returns
due to write lock contention. For most workloads, one worker process with
multiple threads is sufficient.

## What happens if my worker crashes mid-task?

The job stays in `running` status in SQLite. On the next worker start, the
**stale job reaper** detects jobs that have been running longer than their
`timeout` and marks them as failed (triggering retries or DLQ).

If no timeout is set, stale jobs remain in `running` status indefinitely.
**Always set a timeout on your tasks.**

<SdkOnly sdk="python">

```python
@queue.task(timeout=300)  # 5 minute timeout
def process(data):
    ...
```

</SdkOnly>

<SdkOnly sdk="node">

```ts
queue.task("process", process, { timeoutMs: 300_000 }); // 5 minute timeout
```

</SdkOnly>

<SdkOnly sdk="java">

```java
Task<Data> process = Task.of("process", Data.class)
        .timeout(Duration.ofMinutes(5));
```

</SdkOnly>

<SdkOnly sdk="rust">

```rust
#[flexiq::task(timeout = "5m")] // 5 minute timeout
fn process(payload: String) -> flexiq::Outcome<usize> {
    Ok(payload.len())
}
```

</SdkOnly>

## How big can the SQLite database get?

SQLite can handle databases up to 281 TB (theoretical limit). In practice,
flexiq databases stay small if you purge finished jobs. Without cleanup,
expect ~1 KB per job — a million completed jobs ≈ 1 GB.

<SdkOnly sdk="python">

Set `result_ttl` to auto-purge old jobs:

```python
queue = Queue(db_path="myapp.db", result_ttl=86400)  # Purge after 24h
```

</SdkOnly>

<SdkOnly sdk="node">

There is no result-TTL knob; call `purgeCompleted` on a schedule (the argument
is milliseconds):

```ts
setInterval(() => queue.purgeCompleted(86_400_000), 3_600_000); // keep 24h
```

</SdkOnly>

<SdkOnly sdk="java">

There is no result-TTL knob; call `purgeCompleted` on a schedule (the argument
is milliseconds):

```java
flexiq.purgeCompleted(Duration.ofHours(24).toMillis()); // keep 24h
```

</SdkOnly>

<SdkOnly sdk="rust">

The Rust SDK does not expose a queue-wide retention setting. Declare the TTL on
the task instead, and the scheduler's cleanup pass drops the row once it
expires:

```rust
#[flexiq::task(result_ttl = "24h")] // keep results 24h
fn report(day: String) -> flexiq::Outcome<String> {
    Ok(format!("report for {day}"))
}
```

</SdkOnly>

## Can I use a remote or networked SQLite?

No. SQLite requires local filesystem access for file locking. Network
filesystems (NFS, SMB, CIFS) do not reliably support the locking primitives
SQLite depends on. Always place the database on local storage.

## When should I use Postgres instead of SQLite?

Use the **Postgres backend** when you need:

- **Multi-machine workers** — run workers on separate servers sharing the same queue
- **Higher write throughput** — Postgres handles concurrent writers better than SQLite
- **Existing Postgres infrastructure** — leverage your existing database and backups

For single-machine workloads, SQLite is simpler and requires zero setup.

<SdkOnly sdk="python">

Install the extra, then point the queue at Postgres:

```python
# pip install flexiq[postgres]
queue = Queue(db_url="postgres://localhost/flexiq")
```

</SdkOnly>

<SdkOnly sdk="node">

Postgres is already compiled into the prebuilt native binary — no extra install,
just switch the backend:

```ts
new Queue({ backend: "postgres", dsn: process.env.PG_URL, schema: "flexiq" });
```

</SdkOnly>

<SdkOnly sdk="java">

Postgres ships inside the bundled native library — no extra dependency, just
switch the backend:

```java
FlexiQ.builder().postgres(System.getenv("PG_URL")).open();
```

</SdkOnly>

<SdkOnly sdk="rust">

Turn on the `postgres` feature, then open the backend yourself and hand it to
the queue:

```rust
// cargo add flexiq --features postgres
use flexiq::{FlexiQ, PostgresStorage, StorageBackend};

let queue = FlexiQ::from_storage(StorageBackend::Postgres(
    PostgresStorage::new("postgres://localhost/flexiq")?,
))?;
```

</SdkOnly>

See the <SdkLink to="operate/backends">Postgres backend guide</SdkLink>.

## Is flexiq production-ready?

flexiq is suitable for production workloads — background job processing,
periodic tasks, data pipelines, and similar use cases.

For single-machine deployments, use the default SQLite backend. For
multi-server setups, use the <SdkLink to="operate/backends">Postgres backend</SdkLink>.

## What observability options does flexiq support?

<SdkOnly sdk="python">

flexiq offers three observability integrations, each implemented as a
`TaskMiddleware` and combinable:

| Integration | Best for | Install |
|-------------|----------|---------|
| **<SdkLink to="guides/extend">OpenTelemetry</SdkLink>** | Distributed tracing, correlating tasks with HTTP requests | `pip install flexiq[otel]` |
| **<SdkLink to="guides/extend">Prometheus</SdkLink>** | Metrics dashboards, alerting on queue depth/error rates | `pip install flexiq[prometheus]` |
| **<SdkLink to="guides/extend">Sentry</SdkLink>** | Error tracking with rich context and breadcrumbs | `pip install flexiq[sentry]` |

</SdkOnly>

<SdkOnly sdk="node">

flexiq ships three observability middlewares under `@byteveda/flexiq/contrib/*`.
Install the peer you use, then register with `queue.use(...)`:

| Integration | Best for | Peer |
|-------------|----------|------|
| **<SdkLink to="guides/extend">OpenTelemetry</SdkLink>** | Distributed tracing, correlating tasks with HTTP requests | `@opentelemetry/api` |
| **<SdkLink to="guides/extend">Prometheus</SdkLink>** | Metrics dashboards, alerting on queue depth/error rates | `prom-client` |
| **<SdkLink to="guides/extend">Sentry</SdkLink>** | Error tracking with rich context and breadcrumbs | `@sentry/node` |

```ts
import { otelMiddleware } from "@byteveda/flexiq/contrib/otel";
queue.use(otelMiddleware());
```

</SdkOnly>

<SdkOnly sdk="java">

flexiq ships two contrib middlewares, registered with `flexiq.use(...)`. Their
third-party dependency is `compileOnly` — add the runtime dep yourself:

| Integration | Best for | Runtime dep |
|-------------|----------|-------------|
| **<SdkLink to="guides/extend">Micrometer</SdkLink>** (`FlexiQObservation`) | One instrumentation → both a metrics timer and a trace span | `io.micrometer:micrometer-observation` |
| **<SdkLink to="guides/extend">Sentry</SdkLink>** (`SentryMiddleware`) | Error tracking on failed attempts and dead-letters | `io.sentry:sentry` |

```java
flexiq.use(new FlexiQObservation(registry));
```

OpenTelemetry and Prometheus are reached downstream of Micrometer — OTel as a
`micrometer-tracing` backend, Prometheus as the dashboard's `/metrics` endpoint
or a Micrometer `MeterRegistry`. There is no dedicated OTel/Prometheus class.

</SdkOnly>

<SdkOnly sdk="rust">

The Rust SDK has no middleware surface, so there is nothing to hang an
integration on. The nearest seam is `flexiq_core::Worker::on_outcome`, a
callback on every finished job, which `WorkerBuilder` does not expose — build
the worker through `flexiq_core::Worker` directly if you need it. The queue and
the scheduler log through the `log` facade, so whichever logger your binary
installs picks their output up.

</SdkOnly>

## How does flexiq compare to running Celery with SQLite?

Celery can use SQLite as a result backend, but still requires a broker (Redis
or RabbitMQ). flexiq replaces **both** broker and backend with a single
SQLite database. Additionally:

- flexiq's scheduler runs in Rust (faster polling, lower overhead)
- Worker threads are OS threads managed by Rust, not{" "}

```python
@queue.task()

    async with httpx.AsyncClient() as client:
        return [r.text for r in await asyncio.gather(
            *[client.get(url) for url in urls]
        )]
```

Enqueue and await results from async application code:

```python
job = fetch_urls.delay(urls)
result = await job.aresult(timeout=30)

```

<SdkOnly sdk="node">

```ts
queue.task("fetchUrls", async (urls: string[]) =>
```

```ts
const id = queue.enqueue("fetchUrls", [urls]);
```

## What serialization format does flexiq use?

<SdkSwap
  python={<>By default, <code>SmartSerializer</code> — which uses MessagePack with a cloudpickle fallback, so it handles most Python objects including lambdas and closures; switch to <code>JsonSerializer</code> for simpler, cross-language payloads — or provide a custom serializer:</>}
  node={<>By default, <code>JsonSerializer</code> — human-readable JSON bytes; switch to <code>MsgpackSerializer</code> for compact, binary payloads — or provide a custom serializer:</>}
  java={<>By default, <code>JsonSerializer</code> — human-readable JSON bytes via Jackson; switch to <code>MsgpackSerializer</code> for compact, binary payloads — or provide a custom serializer:</>}
  rust={<>One codec, and it is not selectable: arguments and results travel in the cross-SDK CBOR envelope, written by <code>flexiq_core::wire::encode_call</code> and read back by this crate's own <code>ciborium</code> reader. Arguments are positional — a call carrying keyword arguments is refused rather than run with them dropped.</>}
/>

<SdkOnly sdk="python">

```python
from flexiq import Queue, JsonSerializer

queue = Queue(serializer=JsonSerializer())
```

Custom serializers implement the `Serializer` protocol with
`dumps(obj) -> bytes` and `loads(data) -> Any` methods.

</SdkOnly>

<SdkOnly sdk="node">

```ts
import { Queue, MsgpackSerializer } from "@byteveda/flexiq";

new Queue({ dbPath: "flexiq.db", serializer: new MsgpackSerializer() });
```

Custom serializers implement the `Serializer` interface with
`serialize(value) -> bytes` and `deserialize(bytes) -> value` methods.

</SdkOnly>

<SdkOnly sdk="java">

```java
FlexiQ queue = FlexiQ.builder()
    .sqlite("flexiq.db")
    .serializer(new MsgpackSerializer())
    .open();
```

Custom serializers implement the `Serializer` interface with
`serialize(value)` and `deserialize(bytes, type)` methods.

</SdkOnly>

Whatever the codec, avoid passing objects that cannot be serialized — open file
handles, database connections, or thread locks.

## Can I run the dashboard and worker in the same process?

They're designed to run as separate processes sharing the same database.

<SdkOnly sdk="python">

```bash
# Terminal 1
flexiq worker --app myapp:queue

# Terminal 2
flexiq dashboard --app myapp:queue
```

For embedding in a FastAPI app, use `FlexiQRouter` instead — it provides the
same stats and job management as REST endpoints.

</SdkOnly>

<SdkOnly sdk="node">

```bash
# Terminal 1 — run a worker over a module that exports a Queue
flexiq run ./app.js --queues default

# Terminal 2 — serve the dashboard
flexiq --db flexiq.db dashboard --port 8787
```

To embed the dashboard in an existing HTTP server, call `serveDashboard(queue, { port })`.

</SdkOnly>

<SdkOnly sdk="java">

Workers are started programmatically (there is no `flexiq worker` command);
the dashboard has both a programmatic API and a CLI command:

```java
// In your app — start a worker
Worker worker = flexiq.worker().handle(myTask, ...).concurrency(4).start();

// Anywhere — start the dashboard
flexiq.dashboard(8081); // or DashboardServer.start(flexiq, 8081)
```

</SdkOnly>

<SdkOnly sdk="rust">

The Rust SDK serves no dashboard — the `flexiq-server` crate does. A worker is
`queue.worker()…spawn()` inside your own process, so run the server beside it
against the same database.

</SdkOnly>

## How do I reset / clear all jobs?

<SdkOnly sdk="python">

```python
# Purge all completed jobs
queue.purge_completed(older_than=0)

# Purge all dead letters
queue.purge_dead(older_than=0)
```

</SdkOnly>

<SdkOnly sdk="node">

```ts
// Purge all completed jobs and dead letters (argument is milliseconds; 0 = all)
await queue.purgeCompleted(0);
await queue.purgeDead(0);
```

</SdkOnly>

<SdkOnly sdk="java">

```java
// Purge all completed jobs and dead letters (argument is milliseconds; 0 = all)
flexiq.purgeCompleted(0L);
flexiq.purgeDead(0L);
```

</SdkOnly>

<SdkOnly sdk="rust">

`FlexiQ` does not wrap the purges. Reach them on the backend underneath, which
is what `storage()` is for:

```rust
use flexiq::Storage; // the trait the purges live on

// Argument is milliseconds; 0 = all
queue.storage().purge_completed(0)?;
queue.storage().purge_dead(0)?;
```

</SdkOnly>

Or delete the database file and restart:

```bash
rm myapp.db myapp.db-wal myapp.db-shm
```
