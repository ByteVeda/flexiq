## `stats`

```rust
pub fn stats(&self) -> Result<QueueStats>
```

Counts by lifecycle state, across every queue, scoped to the handle's
namespace. The six fields are on
<SdkLink to="api-reference/result">`QueueStats`</SdkLink>.

Per-queue counts are not on `FlexiQ`. `Storage::stats_by_queue` is:

```rust
use flexiq::Storage;

let billing = queue.storage().stats_by_queue("billing", queue.namespace())?;
```

Pausing a queue is on the same trait — `pause_queue(name)`, `resume_queue(name)`
— and likewise not wrapped.

## Choosing a queue

A queue is a name every job carries. There is no queue object to create: naming
one on an enqueue is what makes it exist.

| Where | How | Wins over |
|---|---|---|
| On the task | `#[flexiq::task(queue = "billing")]` | the `"default"` default |
| On the call | `charge::call(..).queue("billing-urgent")` | the declared queue |

A worker pulls from the queues it was told to:

```rust
let worker = queue
    .worker()
    .register::<charge>()
    .queues(["billing", "default"])
    .spawn()?;
```

<Callout type="warn">
  A job on a queue no running worker serves sits `Pending` forever, with nothing
  anywhere reporting it. `WorkerBuilder::queues` defaults to `["default"]`, so a
  task declared `queue = "billing"` needs a worker that names `"billing"` —
  declaring the queue on the task does not enlist a worker for it.
</Callout>

## Namespaces

```rust
let tenant = FlexiQ::open("flexiq.db")?.with_namespace("tenant-a");
```

| Method | Description |
|---|---|
| `with_namespace(impl Into<String>) -> Self` | Scope every operation on this handle to a tenant namespace. |
| `namespace() -> Option<&str>` | The namespace this handle is scoped to, if any. |

A scoped handle carries its namespace into every read, every write, `stats`,
and the worker it builds. The rules are three, and they are checked on the
write path:

| The handle | The call names | Result |
|---|---|---|
| Scoped to `tenant-a` | nothing | Inherits `tenant-a`. |
| Scoped to `tenant-a` | `tenant-a` | Fine — naming its own namespace is not a mismatch. |
| Scoped to `tenant-a` | `tenant-b` | **Refused**, on `enqueue` and on `enqueue_batch`. |
| Unscoped | `tenant-b` | Writes into `tenant-b`. |

The third row is the one that matters. `TaskCall::namespace` is public, so
without the check a caller holding a handle for one tenant could name another
on the call and write into it. A scoped handle is a boundary, not a default.

The fourth is deliberate too: an unscoped handle naming a namespace per call is
how a caller targets one without holding a scoped handle, and stays allowed.

## Periodic administration

Four methods, all on `FlexiQ`:

| Method | Description |
|---|---|
| `list_periodic() -> Result<Vec<PeriodicTask>>` | Every periodic task registered in this handle's namespace. |
| `delete_periodic(name: &str) -> Result<bool>` | Remove a periodic. `false` when this namespace had none by that name. |
| `pause_periodic(name: &str) -> Result<bool>` | Stop a periodic firing, without forgetting it. |
| `resume_periodic(name: &str) -> Result<bool>` | Let a paused periodic fire again. |

`PeriodicTask` carries `name`, `task_name`, `cron_expr`, `args`, `kwargs`,
`queue`, `enabled`, `last_run`, `next_run`, `timezone` and `namespace`. Both
timestamps are Unix milliseconds; `namespace` is the handle's own on every row
a listing returns.

```rust
for task in queue.list_periodic()? {
    println!("{} → {} ({})", task.name, task.cron_expr, task.queue);
}
```

`delete_periodic` removes the row, not the declaration. A worker that still has
the task registered writes it back at its next startup — the schedule lives in
code, and this is the database's copy of it. A pause survives that write: a
declaration owns its cron expression, its timezone and its queue, and nothing
else, so `enabled` is left exactly as an operator set it.

### Scoped to the handle's namespace

A schedule is identified by `(namespace, name)`, so all four reach only the
rows the handle owns, and a namespaced worker writes its declarations into its
own namespace:

```rust
let tenant = FlexiQ::open("flexiq.db")?.with_namespace("tenant-a");

// Only tenant-a's schedules, even if another tenant registered the same name.
for task in tenant.list_periodic()? {
    println!("{} → {}", task.name, task.cron_expr);
}
```

Two tenants sharing a database can both declare a task called `nightly`: each
gets a row of its own, neither sees the other's in a listing, and a delete or a
pause naming a schedule only the other holds returns `false` rather than
reaching it.

<Callout type="info">
  A handle with **no** namespace addresses the default namespace here — one
  namespace, not every tenant's. That is the `NewJob::namespace` rule, not
  `get_job`'s: a schedule has no id of its own, so a name with no namespace
  beside it has to mean a row rather than a wildcard.
</Callout>

The scheduler is the one exception, and it is not addressing a schedule: a
scheduler running without a namespace fires **every** namespace's due rows, and
each job it enqueues lands in the schedule's own namespace.

See <SdkLink to="api-reference/queue/workers">Workers & steps</SdkLink> for
`PeriodicSpec` and how a schedule is declared in the first place.
