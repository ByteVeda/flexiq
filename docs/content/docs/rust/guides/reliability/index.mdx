The engine decides what happens to a job that fails, stalls, or arrives faster
than it can be run. Most of it is declared on the task with
`#[flexiq::task(...)]` and enforced by the scheduler, so a second producer in
another process gets the same behaviour without configuring anything.

## Where each setting lives

Two places, and the split is not arbitrary. Anything that is a property of *one
job* is written onto the job row at enqueue, and a per-call setter overrides it.
Anything that is a property of *the task* is registered with the scheduler when
a worker calls `spawn()`.

| On the job row | On the scheduler |
| --- | --- |
| `queue`, `priority`, `max_retries`, `timeout`, `expires`, `result_ttl` | `retry_backoff_ms`, `retry_max_delay_ms`, `rate_limit`, `retry_budget`, `on_excess`, `max_concurrent`, `max_in_flight_per_task` |

`max_retries` is the one that reaches both: the job carries the budget it was
enqueued with, and the scheduler gets it too so the backoff policy agrees.

```rust
#[flexiq::task(
    max_retries = 5,
    timeout = "30s",
    rate_limit = "100/m",
    on_excess = "defer",
)]
fn charge(order_id: String, cents: i64) -> flexiq::Outcome<i64> {
    let _ = order_id;
    Ok(cents)
}
```

A per-call override touches only the job-row half — there is no per-call rate
limit, because a rate limit is a property of the task across every producer.

```rust
queue.enqueue(charge::call("ord-1".into(), 4_200).timeout_ms(5_000))?;
```
