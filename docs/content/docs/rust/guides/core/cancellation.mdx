---
title: Cancellation
description: "cancel for a pending job, request_cancel and check_cancelled for a running one — what each does."
---

Two methods, two different jobs. A **pending** job is cancelled outright. A
**running** one is asked to stop, and the task has to agree.

```rust
let stopped = queue.cancel(&job_id)?;         // pending only
let asked = queue.request_cancel(&job_id)?;   // running only
```

Both return `bool`, and both are namespace-scoped: a handle scoped to one tenant
gets `false` for an id in another, which is the same answer an unknown id gets.
A scoped caller learns nothing about ids outside its own namespace.

## `cancel` — a pending job

`cancel` archives the job as `Cancelled` and cascade-cancels its dependents, in
one transaction. Nothing is running, so nothing has to cooperate.

```rust
let job = queue.enqueue(charge::call("ord-1".into(), 4_200))?;
assert!(queue.cancel(&job.id)?);
assert!(!queue.cancel("no-such-job")?);
```

`false` means there was nothing to cancel: the id is unknown, or the job is no
longer pending. A job that has already started is not reachable this way — that
is what `request_cancel` is for.

## `request_cancel` — a running job

`request_cancel` sets the cancel-requested flag on a `Running` job and returns.
Nothing interrupts a handler mid-call; the task checks with `check_cancelled`
and unwinds on its own.

```rust
queue.request_cancel(&job.id)?;   // producer side
```

`false` means no running job matched.

## Checking for it

Inside a task body, `flexiq::check_cancelled()` ends the attempt if this job has
been asked to stop:

```rust
#[flexiq::task]
fn reindex(ids: Vec<String>) -> flexiq::Outcome<()> {
    for id in ids {
        flexiq::check_cancelled()?;
        reindex_one(&id)?;
    }
    Ok(())
}
```

It returns `Err(Abort::Cancelled)`, and the pool reports that as `Cancelled`:
the job is archived as cancelled and **not retried** — the retry policy never
sees it. `flexiq::cancel_requested()` answers the same question as a `bool`, for
a body that wants to tidy up before it returns.

Both take no argument, for the same reason `current_step` does: a
macro-declared body is your own function and cannot grow a parameter it did not
declare, so the pool installs the running job on the thread.

The check reads memory, not the database. The worker polls the cancel flag of
everything it has in flight once a second and hands each new request to the
pool, so a cancel made anywhere — this handle, another process, the dashboard —
reaches `check_cancelled` within about a second, and calling it in a tight loop
costs a lock and a set lookup.

Outside a running task, `cancel_requested()` is `false` and `check_cancelled()`
is `Ok(())`.

<Callout type="info">
  Place checks between units of work that are safe to stop after. Nothing
  interrupts the body anywhere else — a task that never checks runs to
  completion, which is the honest behaviour: the alternative is killing a
  thread in the middle of a write.
</Callout>

## Cancellation cascades

Cancelling a job cancels every pending job that depends on it, directly or
transitively, with the reason `dependency cancelled`. The same happens when a
job exhausts its retries and is dead-lettered, with the reason
`dependency failed`. See <SdkLink to="guides/core/dependencies">dependencies</SdkLink>.
