A task is a named function bound to a queue. The name is the contract —
producers enqueue by name, and any worker with that name registered executes
the function and stores its return value as the job's result.

Declaring a task on the queue object means the task module needs the module
that built the queue. To break that coupling — declare tasks without naming a
queue and let one claim them later — see
<SdkLink to="guides/core/discovery">Task discovery</SdkLink>. Everything on this
page applies either way; only the declaration site moves.

## Defining a task

<CodeTabs>
  <Tab sdk="python">

```python
from flexiq import Queue

queue = Queue(db_path="myapp.db")

@queue.task(queue="emails", max_retries=5)
def send_email(to: str, subject: str, body: str) -> str:
    smtp.send(to, subject, body)
    return "sent"
```

  </Tab>
  <Tab sdk="node">

```ts
import { Queue } from "@byteveda/flexiq";

const queue = new Queue({ dbPath: "myapp.db" });

// The name is the contract; the handler runs on a worker and its return is the result.
queue.task(
  "sendEmail",
  async (to: string, subject: string, body: string) => {
    await smtp.send(to, subject, body);
    return "sent";
  },
  { maxRetries: 5 }, // queue is chosen per-enqueue, not here
);
```

  </Tab>
  <Tab sdk="java">

```java
record EmailPayload(String to, String subject, String body) {}

// Producer side: a typed descriptor (name + payload type + defaults).
Task<EmailPayload> sendEmail = Task.of("send_email", EmailPayload.class)
        .queue("emails")
        .maxRetries(5);

// Worker side: bind the logic separately as a TaskFunction.
Worker worker = flexiq.worker()
        .handle(sendEmail, payload -> { smtp.send(payload); return "sent"; })
        .start();
```

For generic payloads that a `Class` token can't express, use a Jackson
`TypeReference` instead: `Task.of("send_email", new TypeReference<Map<String,
Object>>() {})`.

  </Tab>
  <Tab sdk="rust">

```rust
// The name is the function's, unless `name = "..."` says otherwise.
#[flexiq::task(queue = "emails", max_retries = 5)]
fn send_email(to: String, subject: String, body: String) -> flexiq::Outcome<String> {
    smtp::send(&to, &subject, &body).map_err(flexiq::TaskError::retryable)?;
    Ok("sent".to_string())
}

let queue = flexiq::FlexiQ::open("myapp.db")?;

// Producer side: `call(..)` mirrors the function's own argument list.
queue.enqueue(send_email::call(
    "user@example.com".into(),
    "Welcome".into(),
    "…".into(),
))?;

// Worker side: registration is explicit, one `register::<T>()` per task.
let worker = queue.worker().queues(["emails"]).register::<send_email>().spawn()?;
```

`#[flexiq::task]` replaces the function with a type of the same name carrying
three things: `send_email::call(..)` builds an enqueueable value,
`send_email::run(..)` is the original body and stays directly callable from a
unit test, and the `Task` implementation is what `register::<send_email>()`
takes.

  </Tab>
</CodeTabs>

<SdkOnly sdk="java">

### Binding a handler

A `Task<T>` is just a name and a payload type — it's a producer-side
descriptor, not a function. A worker binds the actual logic separately, as a
`TaskFunction<T, R>` that receives the deserialized payload and returns a
result (or `null`):

```java
try (Worker worker = flexiq.worker()
        .handle(sendEmail, payload -> deliver(payload))             // Task + TaskFunction
        .handle("resize", ImageJob.class, payload -> resize(payload)) // name + payload type
        .start()) { ... }
```

`Handler.of(task, fn)` pairs the two for registration via `register(handler)`
or a `HandlerRegistry`. See <SdkLink to="guides/core/workers">Workers</SdkLink>
for the full worker lifecycle.

### Typed tasks from `@TaskHandler`

Annotate handler methods with `@TaskHandler`; the compile-time processor
(`org.byteveda:flexiq-processor`) generates a `<Class>Tasks` companion with a
typed `Task` constant per method plus a `bind(...)` — name declared once, full
generics, zero runtime reflection:

```java
class EmailTasks {
    @TaskHandler("send_email")          // explicit name
    String send(EmailPayload p) { ... }

    @TaskHandler                        // name defaults to "report"
    Report report(List<Metric> metrics) { ... }
}

// generated EmailTasksTasks:
String id = flexiq.enqueue(EmailTasksTasks.SEND, payload);

flexiq.worker()
        .apply(b -> EmailTasksTasks.bind(b, new EmailTasks()))
        .start();
```

The annotation also accepts `queue`, `maxRetries`, `timeoutMs`, `priority`,
`idempotent`, and a `circuitBreakerThreshold` (plus
`circuitBreakerWindowSeconds`/`circuitBreakerCooldownSeconds`/
`circuitBreakerHalfOpenProbes`/`circuitBreakerHalfOpenSuccessRate`) for
per-task defaults. See
<SdkLink to="getting-started/installation">installation</SdkLink> for the
processor setup.

Each companion also carries a nested `Provider` that the processor lists in
`META-INF/services`, so a worker can skip the `bind(...)` line entirely and call
`.discover()` instead — see
<SdkLink to="guides/core/discovery">Task discovery</SdkLink>.

<Callout type="info">
  Register a handler for every task a worker's queues can carry — a job whose
  task has no handler on the claiming worker fails with "no handler
  registered". Re-registering a task name replaces the previous handler.
</Callout>

</SdkOnly>

<SdkOnly sdk="rust">

### Binding a handler

There is no separate descriptor to bind. `#[flexiq::task]` generates the type
*and* keeps the body, and `register::<send_email>()` takes that type — so the
name, the argument types and the handler cannot drift apart:

```rust
let worker = queue
    .worker()
    .register::<send_email>()
    .register::<resize>()
    .spawn()?;
```

`flexiq::Task` is a public trait — `NAME`, `config()`, `defaults()`,
`run_encoded()`, and an optional `periodic()` — so a task with an unusual shape
can implement it by hand and register exactly the same way. The macro is
ergonomics, not plumbing.

<Callout type="info">
  Register every task a worker's queues can carry. A job whose task is not
  registered on the claiming worker fails **fatally** with `task not registered
  on this worker` — no amount of retrying makes it runnable there. Registering
  one name twice is refused by `spawn()` rather than silently replacing the
  first body, because one of the two would never run.
</Callout>

</SdkOnly>

## Task options

Attach retry, timeout, priority, and other execution defaults when you
register the task. Each SDK exposes them with its own names and shape:

<SdkOnly sdk="python">

| Parameter | Type | Default | Description |
|---|---|---|---|
| `name` | `str \| None` | Auto-generated | Explicit task name. Defaults to `module.qualname`. |
| `max_retries` | `int` | `3` | Max retry attempts before moving to DLQ. |
| `retry_backoff` | `float` | `1.0` | Base delay in seconds for exponential backoff. |
| `retry_delays` | `list[float] \| None` | `None` | Per-attempt delays in seconds, overrides backoff. e.g. `[1, 5, 30]`. |
| `max_retry_delay` | `int \| None` | `None` | Cap on backoff delay in seconds (default 300 s). |
| `timeout` | `int` | `300` | Max execution time in seconds (hard timeout). |
| `soft_timeout` | `float \| None` | `None` | Cooperative time limit; checked via `current_job.check_timeout()`. |
| `priority` | `int` | `0` | Default priority (higher = more urgent). |
| `rate_limit` | `str \| None` | `None` | Rate limit string, e.g. `"100/m"`. |
| `queue` | `str` | `"default"` | Named queue to submit to. |
| `circuit_breaker` | `dict \| None` | `None` | Circuit breaker config: `{"threshold": 5, "window": 60, "cooldown": 120}`. |
| `middleware` | `list[TaskMiddleware] \| None` | `None` | Per-task middleware, applied in addition to queue-level middleware. |
| `inject` | `list[str] \| None` | `None` | Worker resource names to inject as keyword arguments. See <SdkLink to="modules/injection/dependency-injection">Resource System</SdkLink>. |
| `serializer` | `Serializer \| None` | `None` | Per-task serializer override. Falls back to the queue-level serializer. |
| `max_concurrent` | `int \| None` | `None` | Max concurrent running instances of this task. `None` means no limit. |

```python
@queue.task(
    name="emails.send",
    max_retries=5,
    retry_backoff=2.0,
    max_retry_delay=60,  # cap backoff at 60 s
    timeout=60,
    priority=10,
    rate_limit="100/m",
    queue="emails",
    max_concurrent=10,
)
def send_email(to: str, subject: str, body: str):
    ...
```

</SdkOnly>

<SdkOnly sdk="node">

| Option | Description |
|---|---|
| `maxRetries` | Attempts before dead-lettering. See <SdkLink to="guides/reliability/retries">retries</SdkLink>. |
| `retryBackoff` | Exponential backoff bounds (`baseMs`, `maxMs`). |
| `timeoutMs` | Per-attempt <SdkLink to="guides/reliability/timeouts">timeout</SdkLink>. |
| `maxConcurrent` | Max simultaneously-running jobs of this task (<SdkLink to="guides/reliability/concurrency">concurrency</SdkLink>). |
| `rateLimit` | <SdkLink to="guides/reliability/rate-limiting">Rate limit</SdkLink> string, `count/unit` (e.g. `"100/m"`). |
| `circuitBreaker` | Trip after repeated failures (<SdkLink to="guides/reliability/circuit-breakers">circuit breakers</SdkLink>). |

```ts
queue.task("add", (a: number, b: number) => a + b, {
  maxRetries: 3,
  retryBackoff: { baseMs: 1000, maxMs: 60_000 },
  timeoutMs: 30_000,
  maxConcurrent: 4,
  rateLimit: "100/m",
  circuitBreaker: { threshold: 5, windowMs: 60_000, cooldownMs: 30_000 },
});
```

<Callout type="info">
  Register a task before enqueuing or running a worker for it. Per-task config
  is applied to the scheduler at registration time — re-registering replaces
  it. There's no task-level default for `queue` or `priority` — set those per
  job with <SdkLink to="guides/core/enqueue-options">enqueue options</SdkLink>
  instead.
</Callout>

Beyond per-task config, set defaults for an entire named queue:

```ts
queue.configureQueue("emails", { rateLimit: "50/s" });
```

<Callout type="info" title="Coming from BullMQ?">
  BullMQ splits a job into `queue.add(name, data)` on one side and a `new
  Worker(queueName, processor)` callback on the other — the processor lives
  wherever you construct the `Worker`. flexiq ties the handler to the task
  name once, via `queue.task(name, handler, options)`; `enqueue()` just
  references that name, and `runWorker()` takes no processor argument. Also
  note: `enqueue()` returns the job id (a `string`), not a rich `Job` object —
  fetch a snapshot with `queue.getJob(id)` or block on
  <SdkLink to="api-reference/result">`queue.result(id)`</SdkLink>.
</Callout>

</SdkOnly>

<SdkOnly sdk="java">

Fluent methods attach default enqueue options; each returns a new descriptor
(the type is immutable):

| Method | Description |
|---|---|
| `queue(name)` | Route jobs to a named queue (<SdkLink to="guides/core/queues">queues</SdkLink>). |
| `priority(n)` | Higher dequeues first within a queue. |
| `retries(n)` / `maxRetries(n)` | Attempts before dead-lettering. |
| `timeout(duration)` / `timeoutMs(ms)` | Per-attempt timeout. |
| `delay(duration)` / `delayMs(ms)` | Delay first execution. |
| `retryPolicy(policy)` | Retry-backoff curve (below). |
| `codecs(names...)` | Named payload codecs applied to this task's payload. |
| `circuitBreaker(config)` | Guard with a `CircuitBreakerConfig` — trips after repeated failures (see [Circuit breakers](#circuit-breakers) below). |
| `withOptions(options)` | Replace the defaults with an `EnqueueOptions` wholesale. |

```java
Task<EmailPayload> sendEmail = Task.of("send_email", EmailPayload.class)
        .queue("emails")
        .priority(5)
        .retries(3)
        .timeout(Duration.ofSeconds(30))
        .delay(Duration.ofSeconds(10));
```

<Callout type="info">
  There's no native per-task `rate_limit` field in the Java SDK — throughput is
  shaped on the producer side with an enqueue gate instead. See
  <SdkLink to="guides/reliability/rate-limiting">rate limiting</SdkLink>.
  Worker resources aren't a `Task` option either — pull them inside the
  handler via `Resources.use("name")` or an `@Resource`-annotated parameter.
  See <SdkLink to="modules/injection/dependency-injection">dependency
  injection</SdkLink>.
</Callout>

</SdkOnly>

<SdkOnly sdk="rust">

`#[flexiq::task]` accepts a closed set of attributes. Anything else is a compile
error that lists the accepted ones:

| Attribute | Value | Default | Effect |
|---|---|---|---|
| `name` | string | the function's name | Task name a job carries, and what a producer in any language enqueues. |
| `queue` | string | `"default"` | Queue each call is enqueued into. |
| `priority` | integer | `0` | Higher dequeues first within a queue. |
| `max_retries` | integer | `3` | Retries before the job dead-letters. |
| `retry_backoff_ms` | duration | `1s` | Base delay of the exponential retry curve. |
| `retry_max_delay_ms` | duration | `5m` | Cap on that curve. |
| `timeout` | duration | `5m` | Cap on one attempt's execution. |
| `expires` | duration | none | Skip the job if it has not started within the window. |
| `result_ttl` | duration | none | How long the archived result is kept. |
| `idempotent` | bare flag, or `= true` | `false` | Derive the dedup key from the task name and payload. |
| `on_excess` | `"defer"` \| `"drop"` | `"defer"` | What happens to a job a rate limit turns away. |
| `max_concurrent` | integer | none | Cluster-wide cap on concurrent runs of this task. |
| `max_in_flight_per_task` | integer | none | This task's share of one worker's in-flight slots. |
| `rate_limit` | rate | none | Dispatch rate cap for this task. |
| `retry_budget` | rate | none | Cap on how fast this task may *retry*, across every job of it. |
| `cron` | string | none | Register the task as a periodic. Six fields, seconds first. |
| `timezone` | string | UTC | IANA name the `cron` expression is read in. Only meaningful beside `cron`. |

A **duration** is `500ms`, `30s`, `5m`, `2h`, `1d`, or a bare unquoted integer of
milliseconds — `timeout = "30s"` and `timeout = 30_000` are the same thing. A
**rate** is `"<count>/<unit>"`, the count at least 1 and the unit one of `s`,
`m`, `h` (or `second`, `minute`, `hour`): `"100/m"`, `"20/s"`, `"1000/h"`. Both
grammars are checked while the macro expands, so a typo is a compile error rather
than a worker that starts and quietly never dispatches.

```rust
#[flexiq::task(
    name = "emails.send",
    queue = "emails",
    priority = 10,
    max_retries = 5,
    retry_backoff_ms = "2s",
    retry_max_delay_ms = "1m",
    timeout = "60s",
    rate_limit = "100/m",
    max_concurrent = 10,
)]
fn send_email(to: String, subject: String, body: String) -> flexiq::Outcome<()> {
    Ok(())
}
```

The set splits in two. `queue`, `priority`, `max_retries`, `timeout`, `expires`,
`result_ttl` and `idempotent` are **enqueue defaults**: they seed every
`send_email::call(..)`, and the matching setter on the call overrides them for
one job. The rest is **scheduler policy**, read once per task when the worker
starts, with no per-call form.

</SdkOnly>

## Retries

Retry scheduling lives in the shared core, so retries stay durable and
survive worker crashes — no in-memory retry state to lose. Backoff is
exponential by default: the delay roughly doubles each attempt, up to a
configurable cap.

<CodeTabs>
  <Tab sdk="python">

```python
@queue.task(max_retries=5, retry_backoff=2.0)
def flaky_api_call(url):
    ...
```

  </Tab>
  <Tab sdk="node">

```ts
queue.task("charge", chargeCard, {
  maxRetries: 5,
  retryBackoff: { baseMs: 1000, maxMs: 60_000 },
});
```

  </Tab>
  <Tab sdk="java">

```java
Task<Order> charge = Task.of("charge", Order.class)
        .maxRetries(5)
        .retryPolicy(RetryPolicy.exponential(Duration.ofSeconds(1), Duration.ofMinutes(1)));
```

  </Tab>
  <Tab sdk="rust">

```rust
// `retry_max_delay_ms` is the cap on the exponential curve.
#[flexiq::task(max_retries = 5, retry_backoff_ms = "1s", retry_max_delay_ms = "1m")]
fn flaky_api_call(url: String) -> flexiq::Outcome<()> {
    fetch(&url).map_err(flexiq::TaskError::retryable)?;
    Ok(())
}
```

Whether a failure is retried at all is the body's call, not the macro's: end a
fallible step with `.map_err(TaskError::retryable)?` to spend a retry, or
`.map_err(TaskError::fatal)?` to dead-letter immediately.

  </Tab>
</CodeTabs>

The cap on the exponential curve is <SdkSwap python={<code>max_retry_delay</code>} node={<code>retryBackoff.maxMs</code>} java={<>the <code>max</code> argument to <code>RetryPolicy.exponential</code></>} rust={<>the <code>retry_max_delay_ms</code> attribute</>} />.

<SdkOnly sdk="python">

Use `retry_delays` for an exact per-attempt wait schedule instead of
exponential backoff — the final value repeats for any further retries up to
`max_retries`:

```python
@queue.task(retry_delays=[1, 5, 30])  # 1s after 1st fail, 5s after 2nd, 30s after 3rd
def flaky_api_call():
    ...
```

</SdkOnly>

<SdkOnly sdk="node">

`retryBackoff` only shapes an exponential curve (`baseMs`, `maxMs`) — there's
no option for an explicit per-attempt delay list.

</SdkOnly>

<SdkOnly sdk="java">

`RetryPolicy.delays(...)` is the explicit per-attempt equivalent — applied
exactly, with no jitter. Supply at least as many delays as `maxRetries`; once
the list is exhausted, further retries fire immediately:

```java
Task<Order> poll = Task.of("poll", Order.class)
        .retries(3)
        .retryPolicy(RetryPolicy.delays(
                Duration.ofSeconds(5), Duration.ofSeconds(30), Duration.ofMinutes(2)));
```

</SdkOnly>

<SdkOnly sdk="rust">

The attribute set shapes the exponential curve only — there is no attribute for
an exact per-attempt schedule. The field the scheduler reads is
`RetryPolicy::custom_delays_ms`, so a task that needs one implements
`flexiq::Task` by hand and returns it from `config()`:

```rust
fn config() -> flexiq::TaskConfig {
    flexiq::TaskConfig {
        retry_policy: flexiq::RetryPolicy {
            max_retries: 3,
            custom_delays_ms: Some(vec![5_000, 30_000, 120_000]),
            ..flexiq::RetryPolicy::default()
        },
        ..flexiq::TaskConfig::default()
    }
}
```

Explicit delays are applied exactly; the exponential path adds full jitter, so
many jobs failing against the same downstream spread out instead of retrying in
a wave.

</SdkOnly>

See <SdkLink to="guides/reliability/retries">Retries</SdkLink> for the full
retry flow and dead-letter behavior.

## Timeouts

A timeout bounds a single execution attempt; exceeding it counts as a failure
and consumes a retry.

<CodeTabs>
  <Tab sdk="python">

```python
@queue.task(timeout=60)
def long_running():
    ...
```

  </Tab>
  <Tab sdk="node">

```ts
queue.task("scrape", scrape, { timeoutMs: 30_000 });
```

  </Tab>
  <Tab sdk="java">

```java
Task<String> scrape = Task.of("scrape", String.class)
        .timeout(Duration.ofSeconds(30));
```

  </Tab>
  <Tab sdk="rust">

```rust
// A duration is `500ms`, `30s`, `5m`, `2h`, `1d`, or a bare integer of ms.
#[flexiq::task(timeout = "60s")]
fn long_running(url: String) -> flexiq::Outcome<()> {
    scrape(&url).map_err(flexiq::TaskError::retryable)?;
    Ok(())
}
```

Per call, `.timeout_ms(60_000)` overrides it. The default is 300 000 ms.

  </Tab>
</CodeTabs>

<SdkOnly sdk="python">

### Soft timeouts

A soft timeout raises `SoftTimeoutError` only when the task cooperatively
checks — useful for a long loop that should stop cleanly instead of being
killed mid-iteration:

```python
from flexiq import current_job

@queue.task(timeout=300, soft_timeout=60)
def long_running(items):
    for item in items:
        current_job.check_timeout()  # raises SoftTimeoutError if soft_timeout exceeded
        process(item)
```

</SdkOnly>

<SdkOnly sdk="node">

See <SdkLink to="guides/reliability/timeouts">Timeouts</SdkLink> for how a
timeout is surfaced to middleware and events, and how to make an `async` task
actually stop work when one fires.

</SdkOnly>

<SdkOnly sdk="java">

See <SdkLink to="guides/reliability/timeouts">Timeouts</SdkLink> — a timeout
releases the job's bookkeeping, not the handler's thread, so long-running
handlers should poll `queue.isCancelRequested(jobId)` to actually stop.

</SdkOnly>

<SdkOnly sdk="rust">

There is no soft timeout and no cooperative check: a task body receives its
decoded arguments and nothing else, so there is no job handle inside it to poll.

The hard timeout is enforced by the scheduler's stale-job sweep, which fails the
job with `job timed out after <n>ms` and frees its slot — it does **not**
interrupt the handler, which keeps running on its blocking thread until it
returns. Bound the work inside the body yourself if that matters: give the HTTP
client its own timeout, or break a long loop on a deadline you read at the top.

</SdkOnly>

## Circuit breakers

Trip a task's circuit breaker after repeated failures so a failing downstream
dependency gets time to recover instead of being hammered by retries. The
breaker opens after `threshold` failures inside a rolling window, then
half-opens after a cooldown to test recovery with a handful of probe jobs.

<CodeTabs>
  <Tab sdk="python">

```python
@queue.task(circuit_breaker={"threshold": 5, "window": 60, "cooldown": 120})
def call_external_api():
    ...
```

  </Tab>
  <Tab sdk="node">

```ts
queue.task("call_flaky_api", callApi, {
  circuitBreaker: { threshold: 5, windowMs: 60_000, cooldownMs: 120_000 },
});
```

  </Tab>
  <Tab sdk="java">

```java
Task<Response> callFlakyApi = Task.of("call_flaky_api", Response.class)
        .circuitBreaker(CircuitBreakerConfig.builder(5)
                .windowSeconds(60)
                .cooldownSeconds(120)
                .build());
```

  </Tab>
  <Tab sdk="rust">

`#[flexiq::task]` has no circuit-breaker attribute. The field the scheduler
reads is `TaskConfig::circuit_breaker`, so a task that needs a breaker
implements `flexiq::Task` by hand and returns one from `config()`:

```rust
fn config() -> flexiq::TaskConfig {
    flexiq::TaskConfig {
        circuit_breaker: Some(flexiq::CircuitBreakerConfig {
            threshold: 5,
            window_ms: 60_000,
            cooldown_ms: 120_000,
            half_open_max_probes: 5,
            half_open_success_rate: 0.8,
        }),
        ..flexiq::TaskConfig::default()
    }
}
```

  </Tab>
</CodeTabs>

Half-open recovery is tunable too: `half_open_probes` / `halfOpenMaxProbes` /
`halfOpenProbes(int)` caps how many probe jobs run while half-open (default
5), and `half_open_success_rate` / `halfOpenSuccessRate` /
`halfOpenSuccessRate(double)` is the probe success rate required to close
again (default 0.8).

<SdkOnly sdk="python">

See <SdkLink to="guides/reliability/circuit-breakers">Circuit
breakers</SdkLink> for the full state machine and how to inspect breaker
state at runtime.

</SdkOnly>

<SdkOnly sdk="node">

See <SdkLink to="guides/reliability/circuit-breakers">Circuit
breakers</SdkLink> — pair it with <SdkLink to="guides/reliability/retries">retries</SdkLink>:
retries absorb transient blips, the breaker stops spending that budget on a
dependency that's actually down.

</SdkOnly>

<SdkOnly sdk="rust">

Breaker state lives in storage, one row per task, so any process pointed at the
same backend can read it. The read is a `Storage` method rather than a `FlexiQ`
one:

```rust
use flexiq::{CircuitState, Storage};

if let Some(row) = queue.storage().get_circuit_breaker("call_external_api")? {
    println!(
        "{:?}, {} failures, opened at {:?}",
        CircuitState::from_i32(row.state),
        row.failure_count,
        row.opened_at
    );
}
```

`list_circuit_breakers()` returns every row at once. `CircuitState` is
`Closed` / `Open` / `HalfOpen`, and `row.state` is the raw `i32` those decode
from.

</SdkOnly>

## Concurrency

<SdkOnly sdk="python">

`max_concurrent` caps how many instances of a task run at once, enforced by
the scheduler across every worker on shared storage — not per worker:

```python
@queue.task(max_concurrent=3)
def expensive_render():
    ...
# At most 3 instances of expensive_render run simultaneously across all workers.
```

</SdkOnly>

<SdkOnly sdk="node">

`maxConcurrent` limits how many jobs of a task run at once across all
workers — enforced by the scheduler against the live running count, so it
holds even with many workers on shared storage:

```ts
queue.task("transcode", transcode, { maxConcurrent: 2 }); // never more than 2 at once
```

Apply it to a whole queue instead with `queue.configureQueue("video", {
maxConcurrent: 4 })`. See
<SdkLink to="guides/reliability/concurrency">Concurrency</SdkLink>.

</SdkOnly>

<SdkOnly sdk="java">

Concurrency in the Java SDK is a **worker-level** setting, not a per-task
field on `Task`: each worker runs its handlers on a thread pool, and the
pool's size caps how many jobs that worker executes at once.

```java
Worker worker = queue.worker()
        .handle(transcode, this::transcode)
        .concurrency(2) // at most 2 handlers run at once on this worker
        .start();
```

To cap a task globally, give it a dedicated queue and size a single worker to
the limit, or serialize the critical section with a
<SdkLink to="guides/reliability/locks">distributed lock</SdkLink>. See
<SdkLink to="guides/reliability/concurrency">Concurrency</SdkLink>.

</SdkOnly>

<SdkOnly sdk="rust">

Two caps, at two scopes. `max_concurrent` is cluster-wide — the scheduler counts
live runs of the task across every worker on shared storage, at the cost of a
database read. `max_in_flight_per_task` is this worker's own pool, in-process and
free, and stops one slow task from occupying every slot:

```rust
#[flexiq::task(max_concurrent = 3, max_in_flight_per_task = 1)]
fn expensive_render(scene: String) -> flexiq::Outcome<()> {
    Ok(())
}
```

The worker's total is `num_workers`, set on the builder and defaulting to 4 —
that bounds every task together, where the two attributes above bound this one.

</SdkOnly>

## Per-task middleware

<SdkOnly sdk="python">

Apply middleware to a specific task only, in addition to queue-level
middleware:

```python
from flexiq.contrib.sentry import SentryMiddleware

@queue.task(middleware=[SentryMiddleware()])
def important_task():
    ...
```

</SdkOnly>

<SdkOnly sdk="node">

Node middleware is registered queue-wide with `queue.use(...)`; there's no
per-task `middleware` option. Scope logic to a task inside the middleware via
`ctx.taskName` in `before` / `after`, or toggle a global middleware per task
from the dashboard (`queue.disableMiddlewareForTask(task, name)`).

</SdkOnly>

<SdkOnly sdk="java">

Java `Middleware` is registered globally with `flexiq.use(...)`; there's no
per-task attachment. Branch inside the middleware on `ctx.taskName()`.

</SdkOnly>

<SdkOnly sdk="rust">

The Rust SDK has no middleware hooks at all, per task or otherwise. The nearest
seam is `flexiq_core::Worker::on_outcome`, a callback handed every processed
outcome — success, retry, dead-letter, cancel — which `WorkerBuilder` does not
expose; building the worker through `flexiq_core::Worker` directly costs you the
durable-step fence this shell's pool carries. For behaviour that belongs to one
task, put it in the body — the function is your own code and nothing intercepts
it on the way in.

</SdkOnly>

## Per-task serializer

<SdkOnly sdk="python">

Override the queue-level serializer for a specific task — the full
round-trip: arguments are serialized with it at enqueue time and deserialized
with it on the worker before the task function is called. Both the sync
worker and the native async worker honor the per-task serializer, falling
back to the queue-level serializer for tasks that have none registered.

```python
from flexiq.serializers import JsonSerializer

@queue.task(serializer=JsonSerializer())
def api_event(payload: dict) -> dict:
    ...
```

Useful when a task needs a different format (e.g., human-readable JSON for
audit tasks) or when the payload isn't picklable. See
<SdkLink to="guides/extend/serializers">Serializers</SdkLink>.

</SdkOnly>

<SdkOnly sdk="node">

The serializer is a queue-level choice (`new Queue({ serializer })`); it can't
be swapped per task. For per-task payload handling, register named `codecs`
(compression / encryption / signing) applied on top of the queue serializer:

```ts
const queue = new Queue({ dbPath: "myapp.db", codecs: { gzip: new GzipCodec() } });
queue.task("audit_event", handleAudit, { codecs: ["gzip"] }); // transform, not a format swap
```

See <SdkLink to="guides/extend/serializers">Serializers</SdkLink>.

</SdkOnly>

<SdkOnly sdk="java">

The serializer is a builder-level choice (`FlexiQ.builder().serializer(...)`);
it can't be swapped per task. For per-task payload handling, use
`Task.codecs(...)` — the same layered-transform model (compression / encryption
/ signing) applied on top of the builder serializer:

```java
Task<AuditEvent> audit = Task.of("audit_event", AuditEvent.class).codecs("gzip");
```

See <SdkLink to="guides/extend/serializers">Serializers</SdkLink>.

</SdkOnly>

<SdkOnly sdk="rust">

The payload codec is the wire CBOR envelope, and it is fixed — there is no
serializer to swap, per task or per queue, and no codec layer on top of it. What
varies is the *types*: any argument that is `serde::Serialize` encodes, and any
parameter that is `serde::de::DeserializeOwned` decodes, so the choice a
serializer would give you is made in the function signature instead.

```rust
#[derive(serde::Serialize, serde::Deserialize)]
struct AuditEvent {
    tenant: String,
    amount_cents: i64,
}

#[flexiq::task]
fn api_event(event: AuditEvent) -> flexiq::Outcome<()> {
    Ok(())
}
```

The writer runs in binary mode — `is_human_readable()` reports `false` — which is
why a type that branches on it, `uuid::Uuid` being the usual one, round-trips as
bytes rather than as a string. Arguments are **positional only**, since Rust has
no keyword arguments, and struct fields keep declaration order: sorting them
would change the `idempotent` dedup key that every language shares.

</SdkOnly>

## Job expiration

<SdkOnly sdk="python">

`expires` skips a job that wasn't started within the deadline. Set a default
on the task, override it per call, or pass it only at enqueue time:

```python
@queue.task(expires=300)  # every job skipped if not started within 5 minutes
def time_sensitive():
    ...

time_sensitive.delay()                      # uses the 300s default
time_sensitive.apply_async(args=(), expires=60)  # tighter window for this call
```

</SdkOnly>

<SdkOnly sdk="node">

The Node SDK has no job-expiration deadline. Job options are `delayMs`
(earliest start) and `timeoutMs` (max run time), but a queued job is never
discarded for sitting too long. Gate stale work inside the handler, or cancel
it with `queue.cancelJob(id)`.

</SdkOnly>

<SdkOnly sdk="java">

The Java SDK has no job-expiration deadline. `EnqueueOptions` offers `delay`
(earliest start) and `timeout` (max run time), but a queued job is never
discarded for sitting too long. Gate stale work inside the handler, or cancel
it with `flexiq.cancelJob(id)`.

</SdkOnly>

<SdkOnly sdk="rust">

`expires` skips a job that has not started within the deadline. Declare a default
on the task, or set it for one call with `.expires_in_ms(..)`:

```rust
#[flexiq::task(expires = "5m")] // skipped if it has not started within 5 minutes
fn time_sensitive(order_id: String) -> flexiq::Outcome<()> {
    Ok(())
}

queue.enqueue(time_sensitive::call("ord-1".into()))?;                       // the 5m default
queue.enqueue(time_sensitive::call("ord-2".into()).expires_in_ms(60_000))?; // tighter, this call only
```

Both are relative and resolved against one `now`, read once at enqueue, so
`expires_at` and a `delay_ms` on the same call cannot disagree by the width of
the call. The sweep that discards an expired job is the scheduler's, so it runs
whether or not a worker ever looked at the queue.

</SdkOnly>

## Task naming

<SdkOnly sdk="python">

By default, tasks are named using `module.qualname`:

```python
# In myapp/tasks.py
@queue.task()
def process():  # Named: myapp.tasks.process
    ...
```

Override with an explicit name:

```python
@queue.task(name="my-custom-name")
def process():  # Named: my-custom-name
    ...
```

</SdkOnly>

<SdkOnly sdk="node">

Node task names are always explicit — the required first argument of
`queue.task(name, handler)`. Unlike Python's `module.qualname` default, there is
no auto-derived name (JS function names are unreliable after bundling).

```ts
queue.task("emails.send", (to: string, subject: string) => send(to, subject));
queue.enqueue("emails.send", ["user@example.com", "Welcome"]);
```

</SdkOnly>

<SdkOnly sdk="java">

`Task.of(name, type)` takes an explicit name. With the `@TaskHandler`
annotation, an empty `value()` defaults the task name to the method name:

```java
@TaskHandler("emails.send")   // explicit name
String send(EmailPayload p) { ... }

@TaskHandler                  // name defaults to the method name: "report"
Report report(List<Metric> m) { ... }
```

</SdkOnly>

<SdkOnly sdk="rust">

A task is named after its function, and `name = "..."` overrides that:

```rust
// In src/tasks/invoices.rs
#[flexiq::task]
fn process() -> flexiq::Outcome<()> { Ok(()) }        // named: process

#[flexiq::task(name = "my-custom-name")]
fn process_v2() -> flexiq::Outcome<()> { Ok(()) }     // named: my-custom-name
```

Deliberately **not** the module path. A path embeds the crate name, so moving the
function between modules — or renaming the binary — would change a name a
producer in another language has to type verbatim.

</SdkOnly>

### Direct call

<SdkOnly sdk="python">

Calling a task directly runs it synchronously, bypassing the queue —
useful in tests:

```python
result = send_email("user@example.com", "Hello", "World")  # Runs immediately
```

</SdkOnly>

<SdkOnly sdk="node">

`queue.task()` returns the queue, not a task object, so there's nothing to
"call directly." Keep a reference to your handler function and invoke it
directly in tests; only `enqueue()` routes through the queue.

```ts
const sendEmail = async (to: string, subject: string) => { /* ... */ return "sent"; };
queue.task("sendEmail", sendEmail);

const result = await sendEmail("user@example.com", "Hi"); // runs now, bypasses the queue
```

</SdkOnly>

<SdkOnly sdk="java">

A `Task<T>` carries no logic to call. Invoke the `TaskFunction` / handler
method directly for a synchronous run; `flexiq.enqueue(task, payload)` is the
only path that goes through the queue.

```java
TaskFunction<EmailPayload, String> send = payload -> smtp.deliver(payload);

String result = send.apply(payload); // runs now, bypasses the queue
```

</SdkOnly>

<SdkOnly sdk="rust">

The macro keeps the original body as `run(..)`, with the function's own
signature, so a task is still callable without a queue — which is how you unit
test one:

```rust
let sent = send_email::run("user@example.com".into(), "Hello".into(), "World".into());
```

Its error type is `Abort`, not `QueueError`: "this attempt failed" and "the queue
could not be reached" are different things, so `?` deliberately does not bridge
them. `call(..)` mirrors the same signature, which is why a wrong argument to an
enqueue is the same compile error as a wrong argument to the function.

</SdkOnly>

## Batch enqueue

Enqueue many jobs of one task in a single storage round-trip:

<CodeTabs>
  <Tab sdk="python">

```python
jobs = send_email.map([
    ("alice@example.com", "Hi", "Body"),
    ("bob@example.com", "Hi", "Body"),
])
```

  </Tab>
  <Tab sdk="node">

```ts
const ids = queue.enqueueMany("sendEmail", [
  { args: ["alice@example.com", "Hi", "Body"] },
  { args: ["bob@example.com", "Hi", "Body"], options: { priority: 5 } },
]);
```

  </Tab>
  <Tab sdk="java">

```java
List<String> ids = flexiq.enqueueMany(sendEmail, List.of(emailA, emailB));
```

  </Tab>
  <Tab sdk="rust">

```rust
// One task per batch: the call's type is the task, and each item keeps its
// own options.
let jobs = queue.enqueue_batch(vec![
    send_email::call("alice@example.com".into(), "Hi".into(), "Body".into()),
    send_email::call("bob@example.com".into(), "Hi".into(), "Body".into()).priority(5),
])?;
```

One item that cannot encode its arguments fails the whole call and writes
nothing. A call carrying a debounce window is refused outright — storage has no
batched debounce, so enqueue that one on its own.

  </Tab>
</CodeTabs>

<SdkOnly sdk="python">

Each item can carry its own overrides. See
<SdkLink to="guides/core/batch-enqueue">Batch enqueue</SdkLink>
for `enqueue_many()`, per-item overrides, and per-item result tracking.

</SdkOnly>

<SdkOnly sdk="node">

Each entry has its own `args` and `options`. See
<SdkLink to="guides/core/enqueue-options">Enqueue options</SdkLink> for the
full batch-enqueue contract, and <SdkLink to="guides/core/batching">Batching</SdkLink>
for the buffering `Batcher` helper built on top of it.

</SdkOnly>

<SdkOnly sdk="java">

Unlike the per-item form above, one shared `EnqueueOptions` applies to the
whole batch — not a list of per-job options. `enqueueAll` is an alias of
`enqueueMany`. See <SdkLink to="guides/core/batching">Batching</SdkLink> for
the buffering `Batcher<T>` helper built on top of it.

</SdkOnly>

<SdkOnly sdk="rust">

Every item carries its own options, because each item *is* a call with the
setters on it. What a batch cannot vary is the task: the call's type is the task,
so one `enqueue_batch` is one task name.

A debounce window is refused rather than split out — storage has no batched
debounce, and looping it item by item would cost the atomicity that is the reason
to send a batch. Enqueue that one on its own. One item whose arguments cannot
encode fails the whole call and writes nothing.

</SdkOnly>
