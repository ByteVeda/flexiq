---
title: Debouncing
description: "Collapse a burst of enqueues into one run on a sliding deadline."
---

Debouncing collapses repeated enqueues that share a key into a **single** job
whose run keeps sliding into the future while the calls keep coming. It is the
answer to "rebuild this user's report once they stop editing", not "run this at
most 100 times a minute" — see
<SdkLink to="guides/reliability/flow-control">Flow control</SdkLink> for how it
differs from throttling and from idempotent coalescing.

<CodeTabs>
  <Tab sdk="python">

```python
@queue.task(
    debounce="5m",                    # slide the run 5 minutes out on every enqueue
    debounce_key="report:{user_id}",  # one window per user
    debounce_max_wait="30m",          # but never delay past 30 minutes
)
def build_report(user_id: str) -> None: ...

first = build_report.delay("u1")      # creates the job
again = build_report.delay("u1")      # same job id — deadline moves
```

  </Tab>
  <Tab sdk="node">

```ts
queue.task("buildReport", buildReport, {
  debounce: "5m", // slide the run 5 minutes out on every enqueue
  debounceKey: "report:{userId}", // one window per user
  debounceMaxWait: "30m", // but never delay past 30 minutes
});

queue.enqueue("buildReport", [{ userId: "u1" }]); // creates the job
queue.enqueue("buildReport", [{ userId: "u1" }]); // same job id — deadline moves
```

  </Tab>
  <Tab sdk="java">

```java
record Report(String userId, int revision) {}

Task<Report> BUILD_REPORT = Task.of("build-report", Report.class)
        .debounce(
                Duration.ofMinutes(5),    // slide the run 5 minutes out on every enqueue
                "report:{userId}",        // one window per user
                Duration.ofMinutes(30));  // but never delay past 30 minutes

String first = flexiq.enqueue(BUILD_REPORT, new Report("u1", 1));  // creates the job
String again = flexiq.enqueue(BUILD_REPORT, new Report("u1", 2));  // same id — deadline moves
```

  </Tab>
  <Tab sdk="rust">

`#[flexiq::task]` takes no debounce attribute, so a window is always named on
the enqueue — and the key is a literal the caller builds, not a template:

```rust
#[flexiq::task]
fn build_report(user_id: String) -> flexiq::Outcome<()> {
    Ok(())
}

let key = format!("report:{user_id}");            // one window per user
let first = queue.enqueue(
    // slide the run 5 minutes out, but never delay past 30 minutes
    build_report::call(user_id.clone()).debounce_ms(key.clone(), 300_000, 1_800_000),
)?;                                               // creates the job
let again = queue.enqueue(
    build_report::call(user_id).debounce_ms(key, 300_000, 1_800_000),
)?;                                               // same job id — deadline moves

assert_eq!(first.id, again.id);
```

  </Tab>
</CodeTabs>

The first enqueue creates the job; every later one with the same resolved key
returns **that** job's id, so a burst of a hundred calls leaves one pending row.
The deadline is `min(now + window, first_seen + max_wait)`, recomputed inside the
same storage operation that finds the open window — two producers racing on one
key cannot both create a job.

A job that has already been claimed is never pulled backwards. If a worker
picked the job up a microsecond ago, the enqueue leaves it alone and inserts a
fresh one instead: the run in flight finishes with the payload it started with,
and the new window opens behind it.

## Durations

## The key is the window

Where the key is a template, it resolves against the arguments of each
individual call — never at registration, since that is where the arguments do
not exist yet.

<SdkOnly sdk="python">

- `{user_id}` names a parameter, whether the caller passed it positionally or by
  keyword; defaults are applied first, and a `**kwargs` parameter is flattened
  so `{user_id}` still resolves for a task declared `def f(**kw)`.
- `{0}`, `{1}`, … name an argument by position — the fallback for a producer
  reaching `queue.enqueue()` with no registered signature to bind against.

```python
@queue.task(debounce="10s", debounce_key="sync:{0}", debounce_max_wait="2m")
def sync_user(user_id: str) -> None: ...
```

</SdkOnly>

<SdkOnly sdk="node">

- `{userId}` reads that property off the first object argument carrying it.
- `{0}`, `{1}`, … read an argument by position.

```ts
queue.task("syncUser", syncUser, {
  debounce: "10s",
  debounceKey: "sync:{0}", // syncUser(userId: string)
  debounceMaxWait: "2m",
});
```

</SdkOnly>

<SdkOnly sdk="java">

- `{userId}` reads that property off the enqueued object — a record component, a
  bean getter, or a `Map` entry, whatever Jackson sees.
- `{owner.id}` walks into a nested object.

```java
Task<Report> SYNC_USER = Task.of("sync-user", Report.class)
        .debounce(Duration.ofSeconds(10), "sync:{userId}", Duration.ofMinutes(2));
```

</SdkOnly>

<SdkOnly sdk="rust">

- There is no placeholder syntax. `debounce_ms(key, window_ms, max_wait_ms)`
  takes the key as a literal, so the interpolation is the caller's, written at
  the call site where the arguments already exist.
- An empty key is refused by the write with `QueueError::Config`, so the global
  window a blank template would open is unreachable here too.

```rust
queue.enqueue(
    sync_user::call(user_id.clone())
        .debounce_ms(format!("sync:{user_id}"), 10_000, 120_000),
)?;
```

</SdkOnly>

A placeholder that resolves to nothing — a missing name, an out-of-range
position, an object where a scalar was expected, or a value that is empty —
<SdkSwap python={<>raises <code>ValueError</code></>} node={<>throws a <code>QueueError</code></>} java={<>throws <code>IllegalArgumentException</code></>} rust={<>cannot happen — the key is a literal string, never a template — though an empty key is refused with <code>QueueError::Config</code></>} />
at enqueue, and nothing is inserted. The alternative would be one global window
silently shared by every caller, which is the failure debouncing exists to
avoid. A template with no placeholder at all is legal and means exactly that:
one window for the whole task.

## Max wait is mandatory

A window with no max wait is refused
<SdkSwap python={<>when the task is registered</>} node={<>when the task is registered</>} java={<>at <code>build()</code> time</>} rust={<>at compile time — <code>Debounce</code> carries all three values at once, so a partial window does not typecheck</>} />,
before any job exists. Without a ceiling, a caller who never stops enqueuing
starves the job forever — the classic debounce footgun. The ceiling is measured
from when the window **opened**, not from the latest call, so the job runs on
schedule no matter how long the burst lasts. It may never be shorter than the
window itself, which would cap the very first insert and make the window
meaningless.

## Which payload runs

By default the job runs with the arguments the window **opened** with; later
enqueues move the deadline and nothing else. Turn on payload replacement to run
with the newest arguments instead:

<CodeTabs>
  <Tab sdk="python">

```python
@queue.task(
    debounce="5m",
    debounce_key="report:{user_id}",
    debounce_max_wait="30m",
    debounce_replace_payload=True,
)
def build_report(user_id: str, revision: int) -> None: ...
```

  </Tab>
  <Tab sdk="node">

```ts
queue.task("buildReport", buildReport, {
  debounce: "5m",
  debounceKey: "report:{userId}",
  debounceMaxWait: "30m",
  debounceReplacePayload: true,
});
```

  </Tab>
  <Tab sdk="java">

```java
Task<Report> BUILD_REPORT = Task.of("build-report", Report.class)
        .debounce(Duration.ofMinutes(5), "report:{userId}", Duration.ofMinutes(30), true);
```

  </Tab>
  <Tab sdk="rust">

`debounce_ms` covers the three-value window; `Debounce` is the whole struct, and
it is where `replace_payload` and the queue admission cap live:

```rust
use flexiq::Debounce;

let window = Debounce {
    replace_payload: true,
    ..Debounce::new(format!("report:{user_id}"), 300_000, 1_800_000)
};

queue.enqueue(build_report::call(user_id, revision).debounce(window))?;
```

  </Tab>
</CodeTabs>

Priority, metadata, notes, dependencies and expiry always belong to the job that
opened the window — only the deadline and, optionally, the payload move. A
coalescing call is a vote to run again soon, not a redefinition of the run.

## Per-enqueue debouncing

The same knobs work on a single submission, so a producer that registers no
handler can still debounce — and where a task carries defaults, one call can
override them:

<CodeTabs>
  <Tab sdk="python">

```python
build_report.apply_async(
    args=("u1",),
    debounce="30s",
    debounce_key="report:{user_id}",
    debounce_max_wait="5m",
)

# Or from a producer process that never imported the task function:
queue.enqueue(
    "build_report",
    args=("u1",),
    debounce="30s",
    debounce_key="report:{0}",
    debounce_max_wait="5m",
)
```

Passing **any** `debounce*` option makes the call define its own window from
scratch — the task's registered values are not merged in, so a per-call
`debounce="1s"` cannot inherit a 30-minute `debounce_max_wait` it never asked
for. Passing none of them uses the task's window, if it has one.

  </Tab>
  <Tab sdk="node">

```ts
queue.enqueue("buildReport", [{ userId: "u1" }], {
  debounce: "30s",
  debounceKey: "report:{userId}",
  debounceMaxWait: "5m",
});
```

An enqueue naming any debounce field layers it over the task's registered
defaults field by field; naming none of them uses the task's window as-is.

  </Tab>
  <Tab sdk="java">

```java
EnqueueOptions urgent = EnqueueOptions.builder()
        .debounce(Duration.ofSeconds(30))
        .debounceKey("report:{userId}")
        .debounceMaxWait(Duration.ofMinutes(5))
        .debounceReplacePayload(true)
        .build();

flexiq.enqueue(BUILD_REPORT, new Report("u1", 3), urgent);
```

`EnqueueOptions.Builder.build()` is where an incomplete set is rejected: a
window with no key, a window with no max wait, a max wait shorter than the
window, or a debounce field set without a window. That is also why
`Task.debounce(...)` takes the whole set in one call — the descriptor is
immutable, so a fluent chain would have to treat a half-set window as valid in
between.

  </Tab>
  <Tab sdk="rust">

Per-enqueue is the only form, so a producer that registers no handler debounces
exactly the way a task author does:

```rust
queue.enqueue(build_report::call("u1".into()).debounce_ms("report:u1", 30_000, 300_000))?;
```

There are no registered defaults to layer over or replace: a call either carries
a whole window or none at all.

  </Tab>
</CodeTabs>

<Callout type="info" title="The override rule is not the same in every SDK">
  A deliberate divergence, not an inconsistency to route around. Python treats
  the `debounce*` set as all-or-nothing: naming any one of them means the call
  defines the whole window, so a one-second window can never inherit a
  thirty-minute ceiling it did not ask for. Node merges field by field, so an
  enqueue can move the window and keep the task's key and max wait. Java replaces
  the task's `EnqueueOptions` wholesale — passing options at all means passing
  every option, debounce included.
</Callout>

## Limits

| Combined with | What happens |
|---|---|
| A dedup key | <SdkSwap python={<><strong>Rejected by the SDK</strong>, before the write</>} node={<><strong>Rejected by the SDK</strong>, before the write</>} java={<><strong>Rejected by the SDK</strong>, before the write</>} rust={<><strong>Not rejected — the window silently wins.</strong> <code>enqueue</code> routes on the debounce window before it looks at the dedup key, so no dedup lookup runs at all</>} />. Two different collapse rules: a dedup key pins the first job and returns it untouched, a window slides it. Covers an explicit key and auto-derived idempotency alike |
| A batch enqueue | **Rejected.** A batch is one storage call with no window to slide — submit debounced jobs one at a time |
| A subscription target | <SdkSwap python={<>The window never engages — a publish is fanned out by the core, one delivery per subscription, and never passes through the enqueue path</>} node={<>Rejected at <code>subscriber()</code> registration — a publish is fanned out by the core and never passes through the enqueue path</>} java={<>Rejected when the subscription is registered — a publish is fanned out by the core and never passes through the enqueue path</>} rust={<>Does not arise — the Rust SDK does not wrap pub/sub, and <code>flexiq_core::pubsub</code> fans a publish out itself without passing through the enqueue path</>} /> |
| A caller-supplied delay | <SdkSwap python={<><strong>Rejected</strong> rather than silently dropped</>} node={<>Ignored — <code>delayMs</code> has no effect</>} java={<><strong>Rejected</strong> rather than silently dropped</>} rust={<>Ignored — <code>delay_ms</code> sets <code>scheduled_at</code>, which the debounce write overwrites</>} />. The deadline is recomputed from the window inside the storage operation, so a delay could never survive |
| An enqueue gate's defer | Ignored. It is a scheduling hint from a <SdkLink to="guides/core/predicates">predicate</SdkLink>, not something the caller asked for, but the window still owns the deadline |
| A queue admission cap | Honoured, but only by the enqueue that inserts. The cap travels into the debounce write and is applied there, so a queue already at its limit still accepts a call that slides the open window — that call adds no pending job for the cap to be about |

<SdkOnly sdk="python">

`idempotent=True` and `batch=` are both rejected at registration next to a
window, not at the first enqueue — an incompatible pair is a configuration
mistake, and import time is when you want to hear about it.

</SdkOnly>

<SdkOnly sdk="rust">

Neither pairing is caught at declaration time. `#[flexiq::task(idempotent)]`
beside a window compiles, and `enqueue` then matches on the window first, so the
`auto:` key is never derived and no dedup lookup runs. The batch case *is*
refused, but at the call rather than at declaration: `enqueue_batch` returns a
`QueueError::Other` naming the task, because storage has no batched debounce to
hand the window to.

</SdkOnly>

## Backends

The slide-or-insert decision, the claimed-row guard and the write are one atomic
step on every backend — see
<SdkLink to="guides/reliability/flow-control">Flow control</SdkLink> for the
per-backend mechanism and what Redis does under contention.

<Callout type="info">
  Debouncing collapses *enqueues*; to bound how fast the jobs you do create

</Callout>
