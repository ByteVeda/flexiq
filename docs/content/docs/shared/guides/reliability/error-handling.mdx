When a <SdkSwap python={<>task raises an exception</>} node={<>task throws (or its promise rejects)</>} java={<>handler throws</>} rust={<>task body returns an <code>Err</code>, or panics</>} />, FlexiQ decides
the job's fate from its retry budget. Each failing attempt is recorded,
then:

1. **Retry** — if attempts remain, the job is rescheduled with
   <SdkLink to="guides/reliability/retries">backoff</SdkLink> (a growing
   delay between attempts, so retries don't hammer a struggling dependency).
2. **Dead-letter** — once the budget is exhausted, the job moves to the
   dead-letter queue, a holding area for permanently-failed jobs you can
   inspect and replay.

<Mermaid
  chart={`flowchart LR
    A["Exception raised"] --> B["Error recorded"]
    B --> C{"Attempts left?"}
    C -->|Yes| D["Reschedule with backoff"]
    C -->|No| E["Move to dead-letter queue"]`}
/>

<CodeTabs>
  <Tab sdk="python">

```python
@queue.task(max_retries=3, retry_backoff=1.0, max_retry_delay=60)
def fetch(url):
    resp = requests.get(url, timeout=10)
    resp.raise_for_status()
    return resp.json()
```

  </Tab>
  <Tab sdk="node">

```ts
queue.task("fetch", fetchUrl, {
  maxRetries: 3,
  retryBackoff: { baseMs: 1000, maxMs: 60_000 },
});
```

  </Tab>
  <Tab sdk="java">

```java
Task<String> FETCH = Task.of("fetch", String.class)
        .maxRetries(3)
        .retryPolicy(RetryPolicy.exponential(Duration.ofSeconds(1), Duration.ofMinutes(1)));
```

  </Tab>
  <Tab sdk="rust">

```rust
#[flexiq::task(max_retries = 3, retry_backoff_ms = "1s", retry_max_delay_ms = "1m")]
fn fetch(url: String) -> flexiq::Outcome<String> {
    let body = http::get(&url).map_err(|e| flexiq::TaskError::retryable(e.to_string()))?;
    Ok(body)
}
```

`Ok` is success and `Err` is failure; which of the two a failure gets is the
constructor's choice, `TaskError::retryable` or `TaskError::fatal`. The macro
will not guess it, and there is no blanket conversion from an arbitrary error
type — that is why the body ends in a `map_err`.

  </Tab>
</CodeTabs>

Returning normally is success; an uncaught throw is failure.

There's no in-task "stop retrying" signal from inside a failing attempt — set
retries to `0` for a fire-once task.

</SdkOnly>

<SdkOnly sdk="node">

There's no in-task "stop retrying" signal from inside a failing attempt — set

</SdkOnly>

<SdkOnly sdk="java">

`TaskFunction` declares `throws Exception`, so checked exceptions propagate
without wrapping. `maxRetries` defaults to `0` — never retry — so a fresh
task is fire-once until you opt into retries.

A failing attempt can also decide for itself: throwing `NonRetryableException`
dead-letters the job immediately, `RetryableException` insists on a retry. See
[Typed signals from the
handler](/java/guides/reliability/retries#typed-signals-from-the-handler).

</SdkOnly>

<SdkOnly sdk="rust">

A failing attempt does decide for itself, and it is the only thing that does:
`TaskError::fatal(..)` dead-letters the job at once whatever budget is left,
`TaskError::retryable(..)` spends one. Set `max_retries = 0` when the whole task
should be fire-once rather than one failure inside it. See
<SdkLink to="guides/reliability/retries">Retries</SdkLink>.

</SdkOnly>

## Timeouts

A per-attempt timeout bounds a single execution attempt. When it elapses,
the attempt is marked failed and timed-out — this consumes a retry like any
other failure, and once the budget is exhausted the job dead-letters with
the timed-out flag set on the outcome, so hooks and event listeners can tell
a timeout apart from other errors.

<CodeTabs>
  <Tab sdk="python">

```python
@queue.task(timeout=30)  # 30 second timeout
def long_task():
    ...
```

  </Tab>
  <Tab sdk="node">

```ts
queue.task("slow", handler, { timeoutMs: 30_000 });
```

  </Tab>
  <Tab sdk="java">

```java
Task<String> SLOW = Task.of("slow", String.class).timeout(Duration.ofSeconds(30));
```

  </Tab>
  <Tab sdk="rust">

```rust
#[flexiq::task(timeout = "30s")]
fn long_task() -> flexiq::Outcome<()> {
    Ok(())
}
```

The pool does not race the handler. The scheduler's stale-job reap notices the
overrun from outside and fails the attempt, so the blocking thread keeps running
until the body returns and its late result is discarded.

  </Tab>
</CodeTabs>

<SdkOnly sdk="python">

The scheduler detects an exceeded timeout externally — its maintenance
reaper checks roughly every 5 seconds — and marks the job failed, which
triggers the retry/DLQ logic above.

</SdkOnly>

<SdkOnly sdk="node">

The dispatcher races the task against the timeout (`tokio::time::timeout`).
For `async` tasks, the timeout aborts the task's
<SdkLink to="guides/core/cancellation">`AbortSignal`</SdkLink> — honor it
(e.g. pass `signal` to `fetch`) so the underlying work actually stops, not
just the bookkeeping.

</SdkOnly>

<SdkOnly sdk="java">

The dispatcher races the handler against the timeout. Unset (or `0`) means
no limit.

</SdkOnly>

<SdkOnly sdk="rust">

The scheduler detects an exceeded timeout externally — its maintenance reap runs
every `reap_interval` polls, roughly every 5 seconds at the default
`SchedulerConfig` — and marks the job failed, which triggers the retry/DLQ logic
above. Nothing races the handler.

Unset is not "no limit" here: `timeout_ms` defaults to 300_000, five minutes, on
every enqueue, and `.timeout_ms(..)` overrides it per call.

</SdkOnly>

<Callout type="warn">
  Timeout reaping marks the job as failed, but it does **not** kill the
  running <SdkSwap python="thread" node="task" java="handler" rust="blocking thread" />: the code
  keeps running until it returns, and the late result is discarded. Always
  set a timeout on production tasks — without one, a wedged
  <SdkSwap python="task" node="task" java="handler" rust="task" /> can hold a worker
  <SdkSwap python="slot" node="slot" java="thread" rust="slot" /> indefinitely.
</Callout>

<SdkOnly sdk="node">

For CPU-bound synchronous work that might hang, honoring `AbortSignal` isn't
enough on its own — see
<SdkLink to="operate/troubleshooting">Troubleshooting: worker is
unresponsive</SdkLink> for offloading it.

</SdkOnly>

<SdkOnly sdk="java">

Make long-running handlers cooperative: poll
`flexiq.isCancelRequested(jobId)` or bound their own blocking calls, so the
underlying work actually stops. See
<SdkLink to="guides/core/cancellation">Cancellation</SdkLink>.

</SdkOnly>

<SdkOnly sdk="rust">

Nothing preempts a blocking thread, so make a long-running body cooperative:
bound its own blocking calls, and poll
`Storage::is_cancel_requested(&job.id, None)` between units of work. That needs
the `Job`, which a macro-expanded body never receives — see
<SdkLink to="guides/core/cancellation">Cancellation</SdkLink> for the
hand-written `Task` impl that does.

</SdkOnly>

<SdkOnly sdk="python">

### Soft timeouts

While the hard timeout above is enforced by the scheduler from the outside,
a **soft timeout** lets the task itself react to time pressure — it's
cooperative, so the task must call `check_timeout()` at safe points:

```python
from flexiq import current_job

@queue.task(soft_timeout=30)
def long_task():
    for chunk in data_chunks:
        process(chunk)
        current_job.check_timeout()  # raises SoftTimeoutError after 30s
```

| Timeout type | Mechanism | Exception |
|---|---|---|
| Hard timeout (`timeout`) | Scheduler reaps the job externally | `TaskTimeoutError` (internal) |
| Soft timeout (`soft_timeout`) | Task checks elapsed time via `check_timeout()` | `SoftTimeoutError` |

</SdkOnly>

<SdkOnly sdk="rust">

### There is no soft timeout

Only the hard one, enforced by the scheduler from outside. A body that wants to
react to time pressure measures it itself and ends the attempt on its own terms:

```rust
use std::time::{Duration, Instant};

#[flexiq::task(timeout = "60s")]
fn long_task(chunks: Vec<String>) -> flexiq::Outcome<()> {
    let deadline = Instant::now() + Duration::from_secs(30);
    for chunk in chunks {
        process(&chunk);
        if Instant::now() > deadline {
            return Err(flexiq::TaskError::retryable("soft deadline passed").into());
        }
    }
    Ok(())
}
```

That spends a retry, exactly as the hard timeout would. Use
`TaskError::fatal` instead when overrunning means the work will never fit.

</SdkOnly>

## Inspecting failures

Every attempt's error is recorded — one entry per failed attempt:

<CodeTabs>
  <Tab sdk="python">

```python
queue.job_errors(job_id)          # one entry per failed attempt
queue.list_jobs(status="failed")
queue.dead_letters()              # exhausted jobs
```

  </Tab>
  <Tab sdk="node">

```ts
await queue.getJobErrors(id); // one entry per failed attempt
await queue.listJobs({ status: "failed" });
await queue.deadLetters(); // exhausted jobs
```

  </Tab>
  <Tab sdk="java">

```java
List<JobError> errors = queue.jobErrors(jobId); // one entry per failed attempt
List<Job> failed = queue.listJobs(JobFilter.builder().status(JobStatus.FAILED).build());
List<DeadJob> dead = queue.listDead(50, 0);     // exhausted jobs
```

  </Tab>
  <Tab sdk="rust">

None of these reads is on `FlexiQ` — `queue.storage()` is the door to them:

```rust
use flexiq::{JobStatus, Storage};

let storage = queue.storage();
let errors = storage.get_job_errors(&job_id, None)?;  // one entry per failed attempt
let failed = storage.list_jobs(Some(JobStatus::Failed as i32), None, None, 50, 0, None)?;
let dead = storage.list_dead(50, 0, None)?;           // exhausted jobs
```

`FlexiQ::list_jobs(limit, offset)` is the unfiltered form. Every listing comes
back blob-free, so `payload` and `result` are empty on these rows — read the
full job with `queue.get_job(&id)`.

  </Tab>
</CodeTabs>

Each error entry carries an id, the job it belongs to, an attempt number
(0-indexed), the error message, and a failure timestamp:

| Field | Description |
|---|---|
| `id` | Unique error record ID |
| <SdkSwap python={<code>job_id</code>} node={<code>jobId</code>} java={<code>jobId</code>} rust={<code>job_id</code>} /> | The job this error belongs to |
| `attempt` | Attempt number (0-indexed) |
| `error` | Error message |
| <SdkSwap python={<code>failed_at</code>} node={<code>failedAt</code>} java={<code>failedAt</code>} rust={<code>failed_at</code>} /> | Timestamp in milliseconds |

<SdkOnly sdk="python">

A job handle also exposes its own history directly:

```python
job = unreliable_task.delay()

for error in job.errors:
    print(f"Attempt {error['attempt']}: {error['error']} at {error['failed_at']}")
```

</SdkOnly>

<SdkOnly sdk="rust">

There is no job handle to hang a history off — `Job` is the row, read back by id.
The most recent failure is on the row itself; the whole history is the storage
read:

```rust
use flexiq::Storage;

if let Some(job) = queue.get_job(&job_id)? {
    println!("last error: {:?}", job.error);  // the canonical TaskError JSON
}

for entry in queue.storage().get_job_errors(&job_id, None)? {
    println!("attempt {}: {} at {}", entry.attempt, entry.error, entry.failed_at);
}
```

`entry.attempt` is the `retry_count` the job carried when that attempt failed, so
the first one is `0`.

</SdkOnly>

### Querying the database directly

For deep debugging, query the jobs table directly (SQLite shown; the same
status codes apply on every backend):

```bash
sqlite3 myapp.db "SELECT id, task_name, status, error FROM jobs WHERE status = 3 LIMIT 10;"
```

Status codes: `0`=pending, `1`=running, `2`=complete, `3`=failed, `4`=dead,
`5`=cancelled.

## Diagnosing dead letters

**Same error on every attempt** — the failure is deterministic (bad
arguments, a missing dependency). Fix the root cause, then replay.
**Intermittent errors** — the failure is transient (a network timeout, a
flaky dependency); replaying will likely succeed.

<CodeTabs>
  <Tab sdk="python">

```python
dead = queue.dead_letters(limit=20)

new_job_id = queue.retry_dead(dead[0]["id"])
```

  </Tab>
  <Tab sdk="node">

```ts
const dead = await queue.deadLetters();

queue.retryDead(dead[0].id); // re-enqueue (preserves notes/metadata)
```

  </Tab>
  <Tab sdk="java">

```java
List<DeadJob> dead = queue.listDead(20, 0);

String newJobId = queue.retryDead(dead.get(0).id); // re-enqueue (preserves metadata)
```

  </Tab>
  <Tab sdk="rust">

```rust
use flexiq::Storage;

let dead = queue.storage().list_dead(20, 0, None)?;
let new_job_id = queue.storage().retry_dead(&dead[0].id, None)?;
```

`retry_dead` takes the dead-letter entry's own `id`, not the
`original_job_id` beside it, and returns the id of the job it created.

  </Tab>
</CodeTabs>

## Cancellation

Cancellation is cooperative — a running <SdkSwap python="task" node="task"
java="handler" rust="task" /> must check for it at safe points; nothing preempts it
mid-execution. One that never checks runs to completion.

<CodeTabs>
  <Tab sdk="python">

```python
from flexiq import current_job

@queue.task()
def long_task(items):
    for item in items:
        process(item)
        current_job.check_cancelled()  # raises TaskCancelledError

# From the caller:
queue.cancel_running_job(job_id)
```

  </Tab>
  <Tab sdk="node">

```ts
import { currentJob } from "@byteveda/flexiq";

queue.task("download", async (url: string) => {
  const { signal } = currentJob() ?? {};
  const res = await fetch(url, { signal });
  return res.text();
});

queue.requestCancel(jobId);
```

  </Tab>
  <Tab sdk="java">

```java
flexiq.requestCancel(jobId); // caller side

// handler side: poll between units of work
for (Chunk chunk : chunks) {
    if (flexiq.isCancelRequested(jobId)) {
        throw new InterruptedException("cancelled");
    }
    process(chunk);
}
```

  </Tab>
  <Tab sdk="rust">

```rust
queue.request_cancel(&job_id)?;  // running job: ask it to stop
queue.cancel(&job_id)?;          // still pending: cancel it outright
```

There is no handle a task body can reach for. A macro-expanded body takes its
decoded arguments and nothing else, so it has no job id to poll with. A
hand-written `Task::run_encoded(job: &Job)` does receive the job:
`job.cancel_requested` is the flag as of dispatch, and
`Storage::is_cancel_requested(&job.id, None)` re-reads it between units of work.

  </Tab>
</CodeTabs>

## Reacting to outcomes

outcome:

## Cleanup on failure

Use a `finally` block (or hooks) to release resources regardless of outcome:

<CodeTabs>
  <Tab sdk="python">

```python
@queue.task()
def process_file(path):
    tmp = download_to_temp(path)
    try:
        return parse(tmp)
    finally:
        os.unlink(tmp)
```

  </Tab>
  <Tab sdk="node">

```ts
queue.task("processFile", async (path: string) => {
  const tmp = await downloadToTemp(path);
  try {
    return await parse(tmp);
  } finally {
    await fs.unlink(tmp);
  }
});
```

  </Tab>
  <Tab sdk="java">

```java
Task<String> PROCESS_FILE = Task.of("process_file", String.class);

queue.worker().handle(PROCESS_FILE, path -> {
    String tmp = downloadToTemp(path);
    try {
        return parse(tmp);
    } finally {
        Files.deleteIfExists(Path.of(tmp));
    }
});
```

  </Tab>
  <Tab sdk="rust">

There is no `finally`; `Drop` is the equivalent, and it covers the `?` path, an
early return and a panic alike:

```rust
/// Removes the temp file however the body leaves.
struct TempFile(std::path::PathBuf);

impl Drop for TempFile {
    fn drop(&mut self) {
        let _ = std::fs::remove_file(&self.0);
    }
}

#[flexiq::task]
fn process_file(path: String) -> flexiq::Outcome<String> {
    let tmp = TempFile(download_to_temp(&path));
    let parsed = parse(&tmp.0).map_err(|e| flexiq::TaskError::retryable(e.to_string()))?;
    Ok(parsed)
}
```

The pool catches a panicking handler, so the unwind that runs `drop` happens
before the failure is recorded.

  </Tab>
</CodeTabs>

## Serialization errors

The default `SmartSerializer` uses MessagePack for common types and falls
back to cloudpickle for anything else. The cloudpickle fallback fails on:

- **Unpicklable objects**: open file handles, database connections, sockets,
  thread locks
- **Module-level objects that can't be resolved**: dynamically generated
  classes without stable import paths
- **Very large objects**: cloudpickle has no hard limit, but extremely large
  payloads slow down SQLite writes

**Fix**: pass simple, serializable data (strings, numbers, dicts, lists) as
task arguments, and reconstruct complex objects inside the task:

```python
# Bad — passing a connection object
@queue.task()
def query(conn, sql):  # conn can't be pickled
    return conn.execute(sql)

# Good — pass connection info, create inside the task
@queue.task()
def query(db_url, sql):
    conn = create_connection(db_url)
    return conn.execute(sql)
```

See [Serialization](/architecture/serialization) for the full serializer
list, including `JsonSerializer` for cross-language or untrusted payloads.

### Exception filtering

Use `retry_on` and `dont_retry_on` to control which exceptions trigger
retries:

```python
@queue.task(
    max_retries=5,
    retry_on=[ConnectionError, TimeoutError],
    dont_retry_on=[ValueError],
)
def call_api(url):
    resp = requests.get(url, timeout=10)
    resp.raise_for_status()
    return resp.json()
```

## Encoding errors

There is no serializer to choose and no fallback codec: a payload is the wire
CBOR envelope, fixed. What can still fail is a value with no representation in
that envelope, and each direction has its own type.

| Type | Returned when |
|---|---|
| `EncodeError` | An argument cannot be written into the call envelope. A `u64` past `i64::MAX` is the ordinary case — nothing widens silently. |
| `DecodeError` | A payload cannot be read back into the task's declared parameter types, including a call whose positional-argument count does not match, or one carrying kwargs. |

An encoding failure is carried on the `TaskCall` rather than raised by `call(..)`
— that call mirrors the task's own signature and has nowhere to put a `Result`,
and a batch stays one expression. It surfaces from `enqueue`, naming the task:

```rust
let err = queue.enqueue(takes_a_big_number::call(u64::MAX)).unwrap_err();
// task `takes_a_big_number` could not encode its arguments: …
```

A decoding failure happens on the worker instead, and it is **fatal** — no
amount of retrying makes a payload decodable — so the job dead-letters with a
message naming the task.

### Fixing it

Pass values the envelope can hold, and reconstruct anything else inside the body
— a task takes its arguments and nothing else, so a connection or a handle was
never going to travel anyway:

```rust
// Bad: a value past i64::MAX has no representation, and `enqueue` says so.
#[flexiq::task]
fn count_rows(upper_bound: u64) -> flexiq::Outcome<u64> {
    Ok(upper_bound)
}
queue.enqueue(count_rows::call(u64::MAX))?;   // Err, naming the task

// Good: pass what identifies the work, and build the rest in the body.
#[flexiq::task]
fn query(db_url: String, sql: String) -> flexiq::Outcome<()> {
    let retry = |e: std::io::Error| flexiq::TaskError::retryable(e.to_string());
    let conn = connect(&db_url).map_err(retry)?;
    conn.execute(&sql).map_err(retry)?;
    Ok(())
}
```

### Testing a task without a worker

`#[flexiq::task]` leaves the body callable: `query::run(..)` is the original
function with its original signature, so a unit test exercises it with no queue,
no storage and no worker. `FlexiQ::in_memory()` is the other half — a private
database that dies with the handle — when the test needs an enqueue as well.

</SdkOnly>

## Exception hierarchy

<SdkOnly sdk="python">

All FlexiQ exceptions inherit from `FlexiQError`, so you can catch the
base class for broad handling:

```
FlexiQError (base)
├── TaskTimeoutError        — hard timeout exceeded
├── SoftTimeoutError        — soft timeout exceeded (check_timeout)
├── TaskCancelledError      — task cancelled (check_cancelled)
├── MaxRetriesExceededError — all retry attempts exhausted
├── SerializationError      — serialization/deserialization failure
├── CircuitBreakerOpenError — circuit breaker is open
├── RateLimitExceededError  — rate limit exceeded
├── JobNotFoundError        — job ID not found (also a KeyError)
└── QueueError              — queue-level operational error
```

```python
from flexiq import FlexiQError, SoftTimeoutError, TaskCancelledError

try:
    result = job.result(timeout=30)
except FlexiQError as e:
    print(f"FlexiQ error: {e}")
```

Import any exception directly from the `flexiq` package:

```python
from flexiq import TaskCancelledError, SoftTimeoutError, SerializationError
```

</SdkOnly>

<SdkOnly sdk="rust">

There is no hierarchy and no base class to catch. Every operation returns
`flexiq::Result<T>`, which is `Result<T, QueueError>` — one enum, so a `match` on
it is exhaustive. The variants a caller usually names:

| Variant | Returned when |
|---|---|
| `JobNotFound(id)` | No job exists with that id. |
| `TaskNotRegistered(name)` | A job referenced a task name with no registered handler. The shell's own pool reports that case as a **fatal** `TaskError` instead, since retrying cannot make the task runnable on that worker. |
| `Serialization(msg)` | A payload or result could not be encoded or decoded. |
| `Config(msg)` | Invalid or inconsistent configuration — an empty debounce key, a `max_wait_ms` below its window. |
| `RateLimitExceeded(key)` | A queue or task rate limit turned the operation away. |
| `QueueFull { queue, pending, cap }` | A debounced enqueue hit the queue's admission cap. The `Display` string is a cross-SDK contract, so the two integers stay at the end where a queue name cannot be mistaken for them. |
| `Timeout(msg)` | A job exceeded its execution timeout. |
| `LockNotAcquired(name)` | A <SdkLink to="guides/reliability/locks">distributed lock</SdkLink> is held by another owner. |
| `ContractTooOld { speaks, required }` | The storage requires a newer contract level than this build speaks. Raised at `FlexiQ::open` / `from_storage`, before anything else runs. |
| `ClaimLost(job_id)` / `StepDiverged { .. }` | A <SdkLink to="modules/steps">durable step</SdkLink> lost its fence, or a commit does not match what is stored at that position. |
| `Storage(_)` / `Pool(_)` | The database, or its connection pool, failed. |
| `Other(msg)` | What the shell refuses by hand: a debounce window riding a batch, a periodic operation on a namespaced handle, one task name registered twice on one worker. |

`TaskError` is the other error type in play and is deliberately not one of these.
A `QueueError` means the queue could not be reached; a `TaskError` means the work
failed. `?` does not bridge them, and a task body's error type is `Abort`, not
`QueueError`, for exactly that reason.

</SdkOnly>
