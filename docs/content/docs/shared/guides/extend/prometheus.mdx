title: Prometheus Metrics
description: "Per-task execution counters and a duration histogram from middleware, plus polled queue depth and dead-letter gauges."
---

Where a binding ships a Prometheus integration, it exports metrics through two
pieces — a middleware that records per-task execution counters and a duration
histogram, and a stats collector that polls queue depth and dead-letter size
onto gauges on an interval. Both write into one
<SdkSwap python={<code>prometheus-client</code>} node={<code>prom-client</code>} java={<code>Micrometer</code>} rust={<>client-library</>} />
registry, so one HTTP endpoint can serve everything.

<SdkOnly sdk="rust">

The Rust SDK ships neither piece, and has no middleware to hang the first one
on. Both halves are still reachable by hand: a
`flexiq_core::Worker::on_outcome` callback is handed every outcome with its
task name and `wall_time_ns`, which is the counter and the histogram, and
`queue.stats()` is the poll behind the gauges. Wire either into whichever
Prometheus client crate you already run.

Reaching the first one has a price worth knowing before you start.
`WorkerBuilder` does not expose `on_outcome`, so that worker is built through
`flexiq_core::Worker` — which runs core's reference pool, and that pool discards
the `(owner, attempt, epoch)` fence a durable step is written under. A task body
that calls `flexiq::current_step()` cannot run on it at all. Counting this way
is a choice *instead of* durable steps, not a layer on top of them.

</SdkOnly>

<SdkOnly sdk="java">

Java has no Prometheus contrib. Metrics come from Micrometer: the
`FlexiQObservation` middleware wraps each task execution in a Micrometer
`Observation`, which a `PrometheusMeterRegistry` turns into a timer (and, if you
add a tracing bridge, a span). See the dedicated
[Micrometer guide](/java/guides/extend/micrometer) for the full API.

## Setup

The SDK compiles against `io.micrometer:micrometer-observation` as `compileOnly`,
so add it plus a Prometheus registry to your build:

- `io.micrometer:micrometer-observation`
- `io.micrometer:micrometer-registry-prometheus` (brings `micrometer-core`, which
  provides `DefaultMeterObservationHandler` and `PrometheusMeterRegistry`)

```java
import io.micrometer.core.instrument.observation.DefaultMeterObservationHandler;
import io.micrometer.observation.ObservationRegistry;
import io.micrometer.prometheusmetrics.PrometheusConfig;
import io.micrometer.prometheusmetrics.PrometheusMeterRegistry;
import org.byteveda.flexiq.contrib.FlexiQObservation;

PrometheusMeterRegistry prometheus = new PrometheusMeterRegistry(PrometheusConfig.DEFAULT);
ObservationRegistry observations = ObservationRegistry.create();
observations.observationConfig()
        .observationHandler(new DefaultMeterObservationHandler(prometheus));

flexiq.use(new FlexiQObservation(observations));
```

## What's emitted

Each execution attempt starts an observation named `flexiq.task` (customizable
via `new FlexiQObservation(registry, name, taskFilter)`) tagged with
`flexiq.task` = the task name. Micrometer's meter handler converts it into a
timer on the Prometheus registry; the exposed series name and suffixes follow
Micrometer's Prometheus naming convention (dots become underscores, a `_seconds`
suffix is added), not a fixed `flexiq_*` name from the contrib. Retries are
separate attempts, each producing its own observation.

## Exposing metrics

Serve `prometheus.scrape()` from any HTTP endpoint, or use Spring Boot Actuator's
`/actuator/prometheus`, which wires the registry for you. The `flexiq_jobs_total`
/ `flexiq_dlq_size` names and the polled queue-depth gauges below are Python/Node
only — build Java dashboards and alerts on the timer series your
Micrometer→Prometheus registry emits.

</SdkOnly>

## Metrics tracked

<SdkOnly sdk="python">

| Metric | Type | Labels | Description |
|---|---|---|---|
| `flexiq_jobs_total` | Counter | `task`, `status` | Total jobs processed (`status` is `completed` or `failed`) |
| `flexiq_job_duration_seconds` | Histogram | `task` | Job execution duration |
| `flexiq_active_workers` | Gauge | — | Number of currently executing workers |
| `flexiq_retries_total` | Counter | `task` | Total retry attempts |
| `flexiq_queue_depth` | Gauge | `queue` | Number of pending jobs, polled by `PrometheusStatsCollector` |
| `flexiq_dlq_size` | Gauge | — | Number of dead-letter jobs, polled |
| `flexiq_worker_utilization` | Gauge | `queue` | Ratio of running jobs to total workers for that queue (0.0–1.0), polled |

The first four are written by `PrometheusMiddleware` as each job runs; the
last three are polled by `PrometheusStatsCollector`. Metrics are created once
per `namespace` and reused, so it's safe to construct the middleware and the
collector independently as long as they share a namespace.

</SdkOnly>

<SdkOnly sdk="node">

| Metric | Type | Labels | Description |
|---|---|---|---|
| `flexiq_jobs_total` | Counter | `task`, `status` | Finished executions by outcome (`status` is `completed` or `failed`) |
| `flexiq_job_duration_seconds` | Histogram | `task` | Execution duration |
| `flexiq_active_workers` | Gauge | — | Jobs currently executing |
| `flexiq_retries_total` | Counter | `task` | Retry attempts |
| `flexiq_queue_depth` | Gauge | `queue` | Pending jobs per queue, polled by `PrometheusStatsCollector` |
| `flexiq_dlq_size` | Gauge | — | Dead-letter queue size, polled |

<Callout type="info">
  There's no `worker_utilization` gauge on Node — `PrometheusStatsCollector`
  only polls queue depth and DLQ size.
</Callout>

</SdkOnly>

<SdkOnly sdk="rust">

None — no series exist, because nothing emits one. What each name above would
have to be assembled from:

| Metric elsewhere | Where the number lives in Rust |
|---|---|
| `flexiq_jobs_total` | Counting `ResultOutcome::Success` and `ResultOutcome::DeadLettered` inside an `on_outcome` callback |
| `flexiq_job_duration_seconds` | `wall_time_ns` on that same outcome — nanoseconds the worker measured, and `0` when nothing measured the run |
| `flexiq_retries_total` | `ResultOutcome::Retry`, whose `retry_count` is the attempt number *after* the failure |
| `flexiq_queue_depth` | `queue.stats().pending`, or `stats_all_queues` through `queue.storage()` for the per-queue split |
| `flexiq_dlq_size` | `queue.stats().dead` |
| `flexiq_active_workers` | `list_workers()` on `queue.storage()` — the cluster registry, not a local count |

One label does not survive the trip. `ResultOutcome::Success` carries `job_id`,
`task_name` and `wall_time_ns` and nothing else; only the other arms — `Retry`,
`DeadLettered`, `Cancelled`, `Slept` — name a `queue`. A per-queue *success*
counter therefore has to come from the polled side rather than the callback.

</SdkOnly>

## Instrumenting job execution

<SdkOnly sdk="python">

Add `PrometheusMiddleware` to your queue to track per-task execution metrics:

```python
from flexiq import Queue
from flexiq.contrib.prometheus import PrometheusMiddleware

queue = Queue(db_path="myapp.db", middleware=[PrometheusMiddleware()])
```

```python
PrometheusMiddleware(
    namespace="myapp",
    disabled_metrics={"resource", "proxy"},
    task_filter=lambda name: not name.startswith("internal."),
)
```

| Parameter | Type | Default | Description |
|---|---|---|---|
| `namespace` | `str` | `"flexiq"` | Prefix for all metric names. |
| `extra_labels_fn` | `Callable[[JobContext], dict[str, str]] \| None` | `None` | Accepted for forward compatibility — not currently applied to any metric's labels. |
| `disabled_metrics` | `set[str] \| None` | `None` | Metric groups or individual names to skip. Groups: `"jobs"`, `"queue"`, `"resource"`, `"proxy"`, `"intercept"`. |
| `task_filter` | `Callable[[str], bool] \| None` | `None` | Predicate that receives a task name. Return `True` to export metrics for the task, `False` to skip it. `None` exports all tasks. |

</SdkOnly>

<SdkOnly sdk="node">

Register `prometheusMiddleware` to record per-job counters and the duration
histogram:

```ts
import { prometheusMiddleware } from "@byteveda/flexiq/contrib/prometheus";

queue.use(prometheusMiddleware());
```

| Option | Type | Default | Description |
|---|---|---|---|
| `namespace` | `string` | `"flexiq"` | Metric name prefix |
| `register` | `Registry` | global `register` | prom-client registry to register metrics into |
| `taskFilter` | `(taskName) => boolean` | — | Return `false` to skip a task |
| `buckets` | `number[]` | prom-client defaults | Histogram bucket boundaries (seconds) |

</SdkOnly>

<SdkOnly sdk="rust">

With no middleware to register, the recording goes in the callback core's
worker accepts:

```rust
use flexiq::{ResultOutcome, Worker};

let worker = Worker::new(queue.storage().clone())
    // Core's worker registers handlers by name over raw bytes, not
    // `#[flexiq::task]` types.
    .register("charge", |_job| Ok(None))
    .on_outcome(|outcome| match outcome {
        ResultOutcome::Success { task_name, wall_time_ns, .. } => {
            observe_duration(task_name, *wall_time_ns);
        }
        ResultOutcome::Retry { task_name, retry_count, .. } => {
            count_retry(task_name, *retry_count);
        }
        // `Slept` is an attempt that ended in a durable sleep rather than a
        // result; `Superseded` is a result the job has already moved past.
        // Counting either as a finished execution overstates both.
        _ => {}
    })
    .spawn()?;
```

`on_outcome` holds one callback, so a second call replaces the first rather
than chaining — put every concern in the same closure. It runs on the worker's
drain thread after the outcome is already recorded, which means a slow exporter
delays result handling for every other job instead of failing this one.
<SdkLink to="guides/extend/monitoring">Monitoring</SdkLink> walks the whole
shape.

</SdkOnly>

## Queue-level metrics

<SdkOnly sdk="python">

For queue-level metrics, use the stats collector. It polls `queue.stats()`
(and resource/proxy/interception stats) on a background thread:

```python
from flexiq.contrib.prometheus import PrometheusStatsCollector

collector = PrometheusStatsCollector(queue, interval=10)
collector.start()
```

```python
PrometheusStatsCollector(
    queue,
    interval=10,
    namespace="myapp",
    disabled_metrics={"intercept"},
)
```

| Parameter | Type | Default | Description |
|---|---|---|---|
| `queue` | `Queue` | — | The Queue instance to poll. |
| `interval` | `float` | `10.0` | Seconds between polls. |
| `namespace` | `str` | `"flexiq"` | Prefix for metric names. Must match `PrometheusMiddleware`'s namespace to share metric objects. |
| `disabled_metrics` | `set[str] \| None` | `None` | Metric groups or names to skip. Same groups as `PrometheusMiddleware`. |

Call `collector.stop()` on shutdown — it signals the background thread and
joins it (up to 5s).

</SdkOnly>

<SdkOnly sdk="node">

`PrometheusStatsCollector` polls queue depth and DLQ size on an interval:

```ts
import { PrometheusStatsCollector } from "@byteveda/flexiq/contrib/prometheus";

const collector = new PrometheusStatsCollector(queue);
collector.start();
```

| Option | Type | Default | Description |
|---|---|---|---|
| `namespace` | `string` | `"flexiq"` | Metric name prefix |
| `register` | `Registry` | global `register` | Registry to write gauges into |
| `intervalMs` | `number` | `10000` | Poll interval in milliseconds |

The internal timer is unref'd, so it never keeps the process alive on its
own. Call `.stop()` on graceful shutdown:

```ts
process.on("SIGTERM", () => {
  collector.stop();
  worker.stop();
});
```

<Callout type="info">
  Metrics for one namespace are built once per registry, so registering
  multiple middlewares is safe. Pass the same `register` to the middleware and
  the collector to keep everything in one registry.
</Callout>

</SdkOnly>

<SdkOnly sdk="rust">

The polled half needs neither a callback nor core's worker — `stats()` on the
handle you already hold is the whole read, and it is scoped to that handle's
namespace:

```rust
use flexiq::Storage;

let stats = queue.stats()?;
set_gauge("queue_depth", stats.pending);
set_gauge("dlq_size", stats.dead);

// Per queue, one escape hatch away.
for (name, per_queue) in queue.storage().stats_all_queues(queue.namespace())? {
    set_labelled_gauge("queue_depth", &name, per_queue.pending);
}
```

`count_pending_by_queue(queue_name)` is the cheaper single-number read when
depth on one lane is all a gauge wants. No collector ships with the crate and
no thread is started for you: call this on an interval of your own, or nothing
ticks at all.

</SdkOnly>

## Exposing metrics

<SdkOnly sdk="python">

Start a standalone `/metrics` endpoint for Prometheus to scrape:

```python
from flexiq.contrib.prometheus import start_metrics_server

start_metrics_server(port=9090)
```

This uses `prometheus_client.start_http_server` under the hood.

### This is a different `/metrics` than the dashboard's

`start_metrics_server` opens its own dedicated HTTP server — it is not the
same endpoint as the dashboard's `GET /metrics` (see
<SdkLink to="modules/dashboard/rest-api">REST API</SdkLink>). Both ultimately
call `prometheus_client.generate_latest()`, but each only serves metrics
registered in *its own process*:

- Run `start_metrics_server` in the same process as your
  `PrometheusMiddleware` / `PrometheusStatsCollector` (typically the worker
  process) — this is the endpoint you'll usually scrape.
- The dashboard's `GET /metrics` only shows something useful if the
  dashboard process itself registered metrics (e.g. it also runs
  `PrometheusMiddleware`). If your worker and dashboard run as separate
  processes — the common deployment — scrape the worker's
  `start_metrics_server` instead.

</SdkOnly>

<SdkOnly sdk="node">

There's no standalone metrics server built in — mount the registry on your
own HTTP server:

```ts
import { register } from "prom-client";
import express from "express";

const app = express();
app.get("/metrics", async (_req, res) => {
  res.set("Content-Type", register.contentType);
  res.end(await register.metrics());
});
```

<Callout type="info">
  The dashboard's own
  <SdkLink to="modules/dashboard/rest-api">`GET /api/metrics`</SdkLink>
  is a separate, JSON-based aggregation, not a Prometheus text-exposition
  endpoint — scrape the server above instead.
</Callout>

</SdkOnly>

<SdkOnly sdk="rust">

The crate opens no socket, so there is no endpoint to start and none to confuse
with a dashboard's. Render the exposition text from whatever HTTP server your
binary already runs.

If you would rather not run one, `flexiq-server` already does: point it at the
same backend and it serves `/metrics` beside the dashboard, gated by
`FLEXIQ_DASHBOARD_METRICS_TOKEN` or a session. What it publishes is
storage-derived and fixed — `flexiq_jobs{queue,status}`, `flexiq_workers`, and
`flexiq_executors` / `flexiq_executor_slots` when executors are attached to it.
None of the per-task names above appear there, because that process runs no task
code of yours and so has nothing to time.

</SdkOnly>

## Full example

<SdkOnly sdk="python">

```python
from flexiq import Queue
from flexiq.contrib.prometheus import (
    PrometheusMiddleware,
    PrometheusStatsCollector,
    start_metrics_server,
)

queue = Queue(db_path="myapp.db", middleware=[PrometheusMiddleware()])

# Start metrics endpoint
start_metrics_server(port=9090)

# Start queue stats polling
collector = PrometheusStatsCollector(queue, interval=10)
collector.start()
```

</SdkOnly>

<SdkOnly sdk="node">

```ts
import { Queue } from "@byteveda/flexiq";
import {
  prometheusMiddleware,
  PrometheusStatsCollector,
} from "@byteveda/flexiq/contrib/prometheus";
import { register } from "prom-client";
import express from "express";

const queue = new Queue({ dbPath: "myapp.db" });
queue.use(prometheusMiddleware());

const collector = new PrometheusStatsCollector(queue);
collector.start();

const app = express();
app.get("/metrics", async (_req, res) => {
  res.set("Content-Type", register.contentType);
  res.end(await register.metrics());
});
app.listen(9090);
```

</SdkOnly>

<SdkOnly sdk="rust">

Both halves in one binary — the counting side on core's worker, the polling
side on a thread beside it:

```rust
use std::thread;
use std::time::Duration;

use flexiq::{FlexiQ, ResultOutcome, Worker};

let queue = FlexiQ::open("myapp.db")?;

let worker = Worker::new(queue.storage().clone())
    .register("charge", |_job| Ok(None))
    .on_outcome(|outcome| {
        if let ResultOutcome::Success { task_name, wall_time_ns, .. } = outcome {
            observe_duration(task_name, *wall_time_ns);
        }
    })
    .spawn()?;

// `FlexiQ` is `Clone`, so the poller takes its own handle instead of sharing
// one behind a lock.
let polled = queue.clone();
thread::spawn(move || loop {
    if let Ok(stats) = polled.stats() {
        set_gauge("queue_depth", stats.pending);
        set_gauge("dlq_size", stats.dead);
    }
    thread::sleep(Duration::from_secs(10));
});

// ... on the way out:
worker.shutdown()?;
```

`shutdown()` is what unregisters this worker — dropping the handle does not, so
a binary that exits without calling it leaves a row in the worker registry for
the reaper to clean up later.

</SdkOnly>

Prometheus scrape config for either SDK:

```yaml
scrape_configs:
  - job_name: flexiq
    static_configs:
      - targets: ["localhost:9090"]
```

## Grafana dashboard tips

<SdkOnly sdk="python">

- **Throughput** — `rate(flexiq_jobs_total[5m])` by `task` and `status`
- **Duration p95** — `histogram_quantile(0.95, rate(flexiq_job_duration_seconds_bucket[5m]))`
- **Queue depth** — `flexiq_queue_depth` by `queue`
- **DLQ size** — `flexiq_dlq_size` with an alert threshold
- **Worker utilization** — `flexiq_worker_utilization` by `queue`

</SdkOnly>

<SdkOnly sdk="node">

- **Throughput** — `rate(flexiq_jobs_total[5m])` by `task` and `status`
- **Duration p95** — `histogram_quantile(0.95, rate(flexiq_job_duration_seconds_bucket[5m]))`
- **Queue depth** — `flexiq_queue_depth` by `queue`
- **DLQ size** — `flexiq_dlq_size` with an alert threshold

</SdkOnly>

<SdkOnly sdk="rust">

There are no series names to hand you — the panels are whatever your callback
and your poller chose to export. Two worth building whatever you called them:

- **Sleeping apart from failing** — give `ResultOutcome::Slept` its own counter
  rather than folding it into `Retry`. A durable sleep spends no retry and is
  not a failure, so a panel that merges the two reads a healthy long-running
  workflow as an incident.
- **Depth beside workers** — `stats().pending` next to the row count from
  `list_workers()`. Depth on its own cannot tell a busy queue from one with
  nothing consuming it.

</SdkOnly>

## Alerting on high DLQ size

Using the same setup as the [full example](#full-example) above, a couple of
alerting rules worth adding — `flexiq_dlq_size` and `flexiq_jobs_total`
carry the same names in the Python and Node exporters, so this rule file
works unchanged for both:

```yaml
groups:
  - name: flexiq
    rules:
      - alert: HighDLQSize
        expr: flexiq_dlq_size > 10
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "flexiq dead letter queue has {{ $value }} entries"
      - alert: HighErrorRate
        expr: rate(flexiq_jobs_total{status="failed"}[5m]) > 0.1
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "High task failure rate: {{ $value }} failures/sec"
```

These expressions assume the default `flexiq` namespace. If you configured a
custom one (`namespace: "myapp"` in the [Options](#options) above), rewrite
the prefixes to match — `myapp_dlq_size`, `myapp_jobs_total` — or the alerts
silently match no series.

<SdkOnly sdk="java">

Java exports metrics through
[Micrometer](/java/guides/extend/micrometer), not this contrib — the
metric names in these rules don't exist there. Build the equivalent alerts on
the names your Micrometer→Prometheus registry emits instead.

</SdkOnly>

<SdkOnly sdk="rust">

Both expressions match nothing on a Rust deployment: neither `flexiq_dlq_size`
nor `flexiq_jobs_total` is ever written, so the rules fire never rather than
loudly. Point them at the names you exported yourself.

If the series come from `flexiq-server` instead, the dead-letter reading is
`flexiq_jobs{status="dead"}` — a gauge of the stored count, so alert on it
crossing a threshold and not on a `rate()`. There is no failure-rate counter to
rewrite `HighErrorRate` against; the nearest equivalent is a rise in
`flexiq_jobs{status="failed"}`.

</SdkOnly>

## Combining with other middleware

<SdkOnly sdk="python">

`PrometheusMiddleware` composes with other middleware:

```python
from flexiq.contrib.otel import OpenTelemetryMiddleware
from flexiq.contrib.sentry import SentryMiddleware

queue = Queue(
    db_path="myapp.db",
    middleware=[
        OpenTelemetryMiddleware(),
        PrometheusMiddleware(),
        SentryMiddleware(),
    ],
)
```

See the <SdkLink to="guides/extend/middleware">Middleware guide</SdkLink>
for more on combining middleware.

</SdkOnly>

<SdkOnly sdk="node">

`prometheusMiddleware` composes with other middleware — register each with
its own `queue.use()` call, in the order you want their hooks to run:

```ts
import { otelMiddleware } from "@byteveda/flexiq/contrib/otel";
import { sentryMiddleware } from "@byteveda/flexiq/contrib/sentry";
import { prometheusMiddleware } from "@byteveda/flexiq/contrib/prometheus";

queue.use(otelMiddleware());
queue.use(prometheusMiddleware());
queue.use(sentryMiddleware());
```

See <SdkLink to="guides/extend/middleware">Middleware</SdkLink> for
more on hook ordering.

</SdkOnly>

<SdkOnly sdk="rust">

There is no stack to compose and no ordering to reason about. `on_outcome`
keeps a single callback — registering a second one drops the first — so metrics,
logging and error reporting share one closure, or live in the task bodies
themselves. <SdkLink to="guides/extend/middleware">Middleware</SdkLink> spells
out what taking the `on_outcome` route costs a task that uses durable steps.

</SdkOnly>
