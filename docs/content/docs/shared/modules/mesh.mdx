---
title: Mesh Scheduling
description: "Gossip-based worker discovery, consistent-hashing affinity, and work-stealing for distributed task dispatch."
---

Workers can form a decentralized **mesh** — SWIM gossip for peer discovery, a
consistent-hash ring for task placement, and TCP work-stealing — so idle
workers pull work from busy peers instead of every worker hammering
[storage](/architecture/storage) on every poll.

Storage remains the source of truth. The mesh only changes *how quickly* a
claimed job reaches an idle worker — if gossip fails entirely, a worker just
falls back to standard polling — so it's safe to add to any worker without
changing dispatch guarantees.

The second worker discovers the first via gossip. Add a third and it only
needs to seed from *any* existing member — gossip propagates the full
membership list from there.

## How it works

Mesh scheduling composes four primitives that work together:

| Primitive | What it does |
|---|---|
| **SWIM gossip** | UDP protocol for peer discovery and failure detection (~1.5s vs a 30s DB heartbeat) |
| **Consistent hashing** | Hash ring with virtual nodes maps each task name to a preferred worker (soft affinity) |
| **Local deque** | In-memory buffer between DB polls, sorted by affinity — workers drain it before hitting [storage](/architecture/storage) again |
| **Work-stealing** | TCP protocol lets idle workers pull jobs from busy peers' deques |

<Mermaid
  chart={`graph LR
    A[Worker A] <--> B[Worker B]
    B <--> C[Worker C]
    A <--> C
    A -. steal .-> B
    Storage[("SQLite / Postgres / Redis")]
    A --- Storage
    B --- Storage
    C --- Storage`}
/>

The database remains the source of truth — an atomic claim is what actually
grants a worker a job. Gossip and stealing are a dispatch-locality
optimization layered on top of that. See
[Architecture: Mesh Scheduling](/architecture/mesh) for the shared engine's
internals, including adaptive prefetch sizing and poll jitter.

## Configuration

All mesh settings live in one place, alongside the worker configuration:

<CodeTabs>
  <Tab sdk="python">

```python
mesh = MeshWorker(
    port=7946,              # gossip UDP port (steal port = port + 1)
    seeds=["host:7946"],    # seed nodes for cluster join
    steal=True,             # enable work-stealing
    affinity_weight=0.7,    # 0.0–1.0, how strongly tasks prefer their hashed worker
    local_buffer=64,        # local deque capacity
    steal_batch=4,          # max jobs stolen per request
    steal_threshold=2,      # steal when own deque ≤ this
    virtual_nodes=150,      # consistent-hash ring virtual nodes per worker
    bind_addr="0.0.0.0",   # network interface to bind
    encryption_key=None,    # base64-encoded key for gossip encryption
    steal_rate_limit=10,    # max steal requests per peer per second
)
```

  </Tab>

Two things differ from a settings object. `steal_port` is a field of its own and
does **not** follow `gossip_port` — `MeshConfig::default()` pins `7947`, so
moving one means moving both. And the SWIM timings are ordinary public fields
here rather than engine constants: `protocol_period_ms` (500),
`indirect_ping_count` (3) and `suspicion_multiplier` (4) are yours to set.

</CodeTabs>

### Parameter reference

Each binding exposes these settings with its own names, defaults, and
validation:

<SdkOnly sdk="python">

| Parameter | Type | Default | Description |
|---|---|---|---|

| `seeds` | `list[str]` | `[]` | Addresses of existing cluster members (`host:port`). |
| `steal` | `bool` | `True` | Whether this worker can steal from and be stolen from. |

| `local_buffer` | `int` | `64` | Max jobs buffered locally before back-pressuring prefetch. |
| `steal_batch` | `int` | `4` | Max jobs transferred per steal request. |
| `steal_threshold` | `int` | `2` | Trigger stealing when own buffer drops to this level. |
| `virtual_nodes` | `int` | `150` | Hash ring virtual nodes per worker. More = more even distribution. |
| `bind_addr` | `str` | `"0.0.0.0"` | Network interface for gossip and steal servers. |
| `encryption_key` | `str \| None` | `None` | Base64 key for XOR gossip encryption. All nodes must share the same key. |
| `steal_rate_limit` | `int` | `10` | Max steal requests accepted per peer per second. `0` = unlimited. |

<SdkOnly sdk="rust">

`MeshConfig` is a plain struct of public fields — no builder, no setters, and
nothing validates a value on the way in. Fill in the ones you care about and
let `..MeshConfig::default()` supply the rest.

| Field | Type | Default | Description |
|---|---|---|---|
| `gossip_port` | `u16` | `7946` | UDP port the SWIM gossip listener binds. |
| `steal_port` | `u16` | `7947` | TCP port the steal server binds. A field of its own — see the note below. |
| `bind_addr` | `String` | `"0.0.0.0"` | Interface both listeners bind. |
| `seeds` | `Vec<String>` | `vec![]` | `host:port` of existing members to join. Empty starts a fresh cluster. |
| `protocol_period_ms` | `u64` | `500` | One SWIM round. Also the upper bound of `poll_jitter_ms()`. |
| `indirect_ping_count` | `usize` | `3` | Peers asked to probe on your behalf when a direct ping goes unanswered. |
| `suspicion_multiplier` | `u32` | `4` | Applied to `ln(N+1) × protocol_period` before a suspect is declared dead. |
| `virtual_nodes` | `usize` | `150` | Points per worker on the hash ring; more spreads ownership more evenly. |
| `local_buffer_capacity` | `usize` | `64` | Local deque capacity. `push_sorted` truncates a batch that would overflow it. |
| `max_steal_batch` | `usize` | `4` | Jobs asked for per steal request. |
| `steal_threshold` | `usize` | `2` | `should_steal()` is true once the deque is at or below this. |
| `affinity_weight` | `f64` | `0.7` | Carried on the struct, but nothing in the engine reads it — see [Task affinity](#task-affinity). |
| `enable_stealing` | `bool` | `true` | Gates `should_steal()`, so it stops this node *initiating* a steal. The steal server still answers peers. |
| `advertise_addr` | `Option<String>` | `None` | A bare IP to advertise. Falls back to `bind_addr`. |
| `encryption_key` | `Option<String>` | `None` | Base64 32-byte key XOR-applied to gossip datagrams. |
| `steal_rate_limit` | `u32` | `10` | Steal requests answered per peer per second. `0` is unlimited. |

<Callout type="warn" title="steal_port does not follow gossip_port">
  The field's own doc comment reads "default: gossip_port + 1", but
  `MeshConfig::default()` hardcodes `7947`. Move `gossip_port` and
  `steal_port` stays where it was — set both, or two nodes on one host will
  fight over the same steal port.
</Callout>

Two fields are quietly forgiving in a way worth knowing. `advertise_addr` goes
through `advertise_ip()`, which parses it as an `IpAddr` — so `"10.0.0.7:7946"`
or a hostname does not parse, and the `unwrap_or` hands back `0.0.0.0`, which no
peer can dial. And `decoded_encryption_key()` answers `None` for anything that
is not valid base64, leaving the node gossiping in the clear. Assert on both at
startup.

</SdkOnly>

<SdkOnly sdk="java">

Set `advertiseAddr` so peers dial back the right host when `bindAddr` stays
`0.0.0.0`.

</SdkOnly>

<SdkOnly sdk="rust">

Across hosts, `advertise_addr` is the field that has to be right. `advertise_ip()`
prefers it and falls back to `bind_addr`, and a `0.0.0.0` bind is not an address
a peer can dial — so leave it unset on a multi-host rollout and the cluster forms
in name only. Give it the pod's or host's own IP, bare:

```rust
let advertise = std::env::var("POD_IP")?;
advertise.parse::<std::net::IpAddr>()?;  // fail here, not silently at 0.0.0.0
```

The two ports are attached to that IP for you — `spawn_gossip` builds the
advertised `gossip_addr` and `steal_addr` from `advertise_ip()` plus
`gossip_port` and `steal_port`, which is why the field takes an IP and not a
`host:port`.

The `threads` argument to `spawn_gossip` is gossiped as this node's `capacity`,
and peers divide the prefetch budget by it — pass the worker's real concurrency,
not a placeholder. Its `queues` argument is likewise the list peers see, and
nothing cross-checks it against `.queues([...])` on the builder: they are two
separate lists you have to keep equal.

</SdkOnly>

<Callout type="warn" title="Firewall rules">
  Workers need UDP (gossip) and TCP (steal) access to each other. Open both
  the gossip port and the steal port (gossip + 1) between all mesh workers.
</Callout>

<SdkOnly sdk="node">

<Callout type="info" title="No CLI flags for mesh">
  The `flexiq run ./app.js` CLI command has no mesh options — mesh is only
  enabled by passing `mesh` to `runWorker()` in your own code. Read the
  config from the environment in your entrypoint instead:
</Callout>

```ts
// worker-entry.ts — container entrypoint, reads mesh config from env vars

const queue = new Queue({ dbPath: "tasks.db" });
```

## Task affinity

The consistent-hash ring maps each task name to a preferred worker. When a
worker prefetches a batch of jobs, it sorts them before pushing them into
the local deque:

- **Owned tasks** (hashed to this worker) go to the back of the deque —
  popped first
- **Non-owned tasks** go to the front — left there for peers to steal

Any worker can still run any task — affinity only biases *which worker gets
to it first*. This improves cache locality: when a task consistently lands
on the same worker, its open connections, warm caches, and worker-scoped
<SdkLink to="modules/injection/dependency-injection">resources</SdkLink> stay
hot instead of being rebuilt everywhere.

### Watch a routing key pick its pool

Each job carries a key that decides which pool of workers is built to run it.
Drop a machine and its work reroutes across the rest of that pool rather than
stalling.

<TaskAffinityDemo />

<SdkOnly sdk="python">

The `affinity_weight` parameter controls how aggressively the ring biases
dispatch — `0.0` disables affinity entirely, `1.0` is a strict preference:

```python
# High affinity — tasks strongly prefer their hashed worker
mesh = MeshWorker(affinity_weight=1.0)

# No affinity — pure load-balancing, no task-to-worker preference
mesh = MeshWorker(affinity_weight=0.0)
```

</SdkOnly>

<SdkOnly sdk="node">

<Callout type="info">
  `affinityWeight` on the mesh config is reserved but currently unused —
  the sort above is a hard owned/non-owned split, not a tunable strength.
  There's no option today to dial affinity up or down.
</Callout>

</SdkOnly>

<SdkOnly sdk="java">

`affinityWeight` controls the same tradeoff:

```java
// Strict — tasks strongly prefer their hashed worker
MeshOptions.builder().affinityWeight(1.0).build();

// None — pure load-balancing, no task-to-worker preference
MeshOptions.builder().affinityWeight(0.0).build();
```

</SdkOnly>

<SdkOnly sdk="rust">

`MeshConfig::affinity_weight` exists and defaults to `0.7`, but the engine never
reads it — `LocalDeque::push_sorted` partitions a batch into owned and non-owned
and nothing consults a weight. Setting it to `0.0` or `1.0` changes nothing
today.

The split itself is a function you can call:

```rust
if node.is_affinity_owner("process_order") {
    // this node is the ring owner for that task name
}
```

`prefetch` calls it once per job and pushes accordingly: owned to the back, which
`pop_local()` takes first, and non-owned to the front, which is the end
`give_jobs()` hands to a thief. The knob that actually moves placement is
`virtual_nodes` — it controls how evenly names spread over the ring, not how
hard the deque prefers them.

</SdkOnly>

## Work-stealing

When a worker's local buffer drops to its steal threshold, it looks at
gossip-reported buffer lengths across the cluster, picks the busiest peer,
and opens a TCP connection to that peer's steal port requesting a batch of
jobs.

The victim pops jobs from the cold end of its deque (non-owned tasks first)
and sends them back. The thief executes them locally — no DB round-trip
needed, since the jobs are already claimed as running in storage. Stealing
is rate-limited per peer to prevent thundering-herd effects.

<SdkOnly sdk="node">

The worker only steals from peers with enough surplus (steal threshold +
steal batch). The connect attempt times out after 500ms and the response
after 2s, so a stuck peer doesn't stall dispatch.

</SdkOnly>

<SdkOnly sdk="rust">

Nothing drives that loop for you — `MeshNode::try_steal` is an async method you
call, and it returns how many jobs came back:

```rust
if node.should_steal() {
    let stolen = node.try_steal().await;  // already pushed into the local deque
}
```

It bails early unless `should_steal()` holds, then asks `best_steal_target` for
the busiest alive peer whose gossiped `local_buffer_len` is strictly greater than
`steal_threshold + max_steal_batch`. Below that surplus there is no target and
the call returns `0`. Connecting is capped at 500ms and the reply at 2s, so a
wedged peer costs a round, not the loop.

One counter to read with care: `steals_initiated` is bumped before the
connection, so a failure to connect, write, read or decode is counted as an
attempt. A gap from `steals_succeeded` means attempts are not paying off — it
does not specifically mean peers were empty.

</SdkOnly>

Work-stealing is on by default — workers automatically balance load across
the cluster. When one worker gets a burst of jobs, idle peers steal the
overflow within milliseconds. Disabling it stops this worker from
participating in steals:

<CodeTabs>
  <Tab sdk="python">

```python
mesh = MeshWorker(steal=False)
```

Workers still benefit from gossip discovery, consistent hashing, and local
deque prefetch — but won't steal from or donate jobs to peers. Useful when
tasks have strong per-worker state dependencies.

  </Tab>
  <Tab sdk="node">

```ts
queue.runWorker({ mesh: { port: 7946, steal: false } });
```

<Callout type="info" title="steal: false is one-directional">
  Setting `steal: false` only stops *this* worker from initiating steals —
  the TCP steal server always runs, so this worker will still hand jobs to
  any peer that asks (subject to `stealRateLimit`). Use it on a worker you
  don't want draining its own queue to help others, not to shield a worker
  from ever donating work.
</Callout>

  </Tab>
  <Tab sdk="java">

```java
MeshOptions.builder().enableStealing(false).build();
```

Gossip discovery, consistent hashing, and local-deque prefetch keep
running — the worker just won't steal from or donate jobs to peers. Useful
when tasks have strong per-worker state.

  </Tab>
  <Tab sdk="rust">

```rust
MeshConfig { enable_stealing: false, ..MeshConfig::default() };
```

The flag is read by `should_steal()` only, so it stops the steals this node
*initiates*. `spawn_steal_server()` still serves peers that ask, subject to
`steal_rate_limit` — skip the call entirely if this node must never donate.

  </Tab>
</CodeTabs>

### Tuning work-stealing

<SdkOnly sdk="python">

| Scenario | Recommended settings |
|---|---|
| Bursty, short tasks | `steal_batch=8, steal_threshold=4` — steal more, earlier |
| Long-running tasks | `steal_batch=1, steal_threshold=1` — steal conservatively |
| Many workers (10+) | `steal_rate_limit=5` — prevent steal storms |
| Few workers (2–3) | `steal_rate_limit=0` — unlimited, low contention |

</SdkOnly>

| Scenario | `MeshConfig` fields |
|---|---|
| Bursty, short tasks | `max_steal_batch: 8, steal_threshold: 4` — steal more, earlier |
| Long-running tasks | `max_steal_batch: 1, steal_threshold: 1` — steal conservatively |
| Many nodes (10+) | `steal_rate_limit: 5` — cap what each peer will answer |

Raising the pair also raises the surplus a peer must show before it counts as a
target: `try_steal` requires `local_buffer_len > steal_threshold +
max_steal_batch`, so `8`/`4` needs a peer holding thirteen buffered jobs. Push
both high enough and no peer ever qualifies.

`enable_stealing: false` only gates `should_steal()`. The steal server still
runs once you have called `spawn_steal_server`, so the node keeps donating jobs
while refusing to take any — skip the spawn to opt out of both.

</SdkOnly>

  </Tab>
  <Tab sdk="java">

```java

        .port(7946)
        .seed("10.0.0.2:7946")
        .encryptionKey(System.getenv("MESH_KEY")) // 32-byte key, base64-encoded
```

  </Tab>
  <Tab sdk="rust">

```rust
let config = MeshConfig {
    seeds: vec!["10.0.0.2:7946".to_string()],
    encryption_key: Some(std::env::var("MESH_KEY")?),  // 32 bytes, base64
    ..MeshConfig::default()

```

`decoded_encryption_key()` is where the string becomes bytes, and it answers
`None` for anything it cannot decode rather than failing — check it at startup,
or a typo leaves this node gossiping in the clear while its peers do not.

  </Tab>
</CodeTabs>

All nodes in the cluster must use the same key. Nodes with mismatched keys
fail to decode each other's gossip messages and never join the cluster.

<Callout type="warn" title="Encryption scope">
  Gossip encryption XOR-obfuscates the UDP membership protocol only — it
  deters casual sniffing, not a determined attacker. Work-stealing traffic
  over TCP is never encrypted. For real transport security, put mesh traffic
  on a private network (WireGuard, VPN, or a service mesh).
</Callout>

### Inspecting the cluster

`Worker.meshClusterInfo()` returns an `Optional<MeshClusterInfo>` — empty
unless the worker was started with `.mesh(...)`:

```java
worker.meshClusterInfo().ifPresent(cluster ->
        log.info("peers={} load={} buffered={} prefetch={}",
                cluster.peerCount(), cluster.totalLoad(),
                cluster.totalBuffered(), cluster.adaptivePrefetch()));
```

| `MeshClusterInfo` field | Description |
|---|---|
| `peerCount()` | Alive peers discovered via gossip (excludes this node). |
| `totalCapacity()` | Summed advertised capacity across those peers. |
| `totalLoad()` | Summed in-flight jobs across those peers. |
| `totalBuffered()` | Summed local-deque length across those peers. |
| `localBufferLen()` | This worker's own local-deque length. |
| `adaptivePrefetch()` | This worker's current prefetch budget. |

</SdkOnly>

<SdkOnly sdk="rust">

Because you hold the `MeshNode`, the counters are a method call rather than an
exported endpoint. Two snapshots, both `Serialize`, so either drops straight into
whatever you already scrape:

```rust
let m = node.metrics();      // MetricsSnapshot
let c = node.cluster_info(); // ClusterInfo

log::info!(
    "peers={} buffered={} prefetch={} stolen_in={} stolen_out={}",
    c.peer_count, c.local_buffer_len, c.adaptive_prefetch,
    m.jobs_stolen_in, m.jobs_stolen_out,
);
```

| `MetricsSnapshot` field | What it counts |
|---|---|
| `prefetch_count` | Batches handed to the deque — how often you topped up, not how much you fetched. |
| `prefetch_jobs` | Jobs those batches actually buffered. Short of what was offered once capacity is reached. |
| `local_pops` | Jobs taken off the hot end to run here. The mesh's useful output. |
| `steals_initiated` | Attempts started, counted before the connection — failures are in here. |
| `steals_succeeded` | Attempts that returned at least one job. |
| `jobs_stolen_in` | Jobs received from peers. Rises when this node is the idle one. |
| `jobs_stolen_out` | Jobs surrendered to thieves. Rises when this node is the buffered-up one. |
| `ring_recalculations` | Ring rebuilds. A fast climb is affinity thrashing. |

`ClusterInfo` carries `peer_count`, `total_capacity`, `total_load`,
`total_buffered`, `local_buffer_len` and `adaptive_prefetch`. Only
`local_buffer_len` is exact — the peer sums are as of each peer's last gossip,
so they are at least one `protocol_period_ms` stale. The counters are
free-running atomics loaded `Relaxed` and never reset, so a rate needs two
snapshots and a clock.

For the narrative, `flexiq-mesh` logs through the `log` facade, so the output
appears once *your* binary installs a logger:

```bash
RUST_LOG=flexiq_mesh=debug ./my-worker          # everything the mesh does
RUST_LOG=flexiq_mesh::swim=info ./my-worker     # membership changes only
RUST_LOG=flexiq_mesh::steal=debug ./my-worker   # steal attempts and donations
```

</SdkOnly>

## Graceful shutdown

When a mesh worker shuts down, it broadcasts a `Leave` message to all known
peers. They remove it from the ring immediately — no suspicion timeout
needed.

<SdkOnly sdk="python">

Triggered via `Ctrl+C`, `SIGTERM`, or
<SdkLink to="guides/core/workers#programmatic-shutdown">programmatic
shutdown</SdkLink>.

</SdkOnly>

<SdkOnly sdk="node">

```ts
process.on("SIGTERM", () => worker.stop());
```

`stop()` broadcasts the leave message before the gossip loop exits.

</SdkOnly>

<SdkOnly sdk="java">

`worker.close()` (and `stop()`) signal the mesh node before the native
worker tears down, which broadcasts the leave message.

</SdkOnly>

<SdkOnly sdk="rust">

`MeshNode::request_shutdown()` is the signal. The gossip loop's shutdown arm is
where `broadcast_leave` runs, so the `Leave` only goes out if that loop is the
one that wakes:

```rust
let gossip = node.spawn_gossip(vec!["default".to_string()], 4);
let stealer = node.spawn_steal_server();

// … later, on SIGTERM
node.request_shutdown();
node.request_shutdown();  // one signal per spawned loop — see below
let _ = tokio::join!(gossip, stealer);
```

<Callout type="warn" title="One signal wakes one loop">
  `request_shutdown` calls `Notify::notify_one` on a handle both loops await.
  Two tasks are waiting and one call wakes one of them, so a single call leaves
  the other running — and if the steal server is the one that wakes, no leave
  message is ever broadcast and peers fall back to the suspicion timeout.
  Signal once per loop you spawned, then join the handles.
</Callout>

Awaiting the `JoinHandle`s is what makes shutdown ordered: both are plain
`tokio::spawn`s, so dropping the runtime instead just cancels them mid-flight.

</SdkOnly>

If a worker crashes without leaving, the SWIM failure detector kicks in:
direct ping fails → indirect ping via intermediaries → suspicion → declared
dead after `suspicion_multiplier × ln(N+1) × protocol_period`. With default
settings (multiplier `4`, 500ms period), a crashed worker in a 3-node
cluster is typically detected in about `4 × ln(4) × 500ms ≈ 2.8s`. These
SWIM timing knobs are fixed by the core engine and aren't exposed as
configuration options.

## When to use mesh

<SdkOnly sdk="python">

**Good fit:**
- Multiple workers processing the same queues (2+ workers)
- High job throughput where DB polling is a bottleneck
- Tasks that benefit from cache locality (imports, connections, warm state)
- Environments where sub-second failure detection matters
- Horizontal scaling where workers come and go frequently

**Not needed:**
- Single worker setups
- Low throughput (&lt; 100 jobs/second)
- Workers processing completely different queues (no overlap = no stealing)
- Already using [bare-metal autoscaler](/python/modules/autoscaling)
  or [KEDA](/python/modules/autoscaling/keda) for process-level scaling (mesh
  is *within-process* optimization, not a replacement for autoscaling)

<SdkOnly sdk="rust">

Start from what it costs here. `WorkerBuilder` has no mesh option, so a
`MeshNode` does not feed `queue.worker()` — the worker keeps polling storage and
never looks at the local deque. Running both gives you gossip and a buffer that
nothing drains. Reaching for the mesh means writing the dispatch loop yourself
against `queue.storage()`, with `should_prefetch`, `adaptive_prefetch_size`,
`prefetch`, `pop_local` and `try_steal` as its parts.

**Worth that:**
- You already run a custom dispatch loop, and polling latency is the bottleneck
- Several Rust nodes on the same queues, where sub-second peer detection beats a
  30-second heartbeat
- Work that gains from landing on the same node — warm connections, a populated
  cache, anything a `OnceLock` static holds
- A fleet whose nodes come and go often enough that ring churn is cheaper than
  waiting out a heartbeat

**Not worth it:**
- One node, or nodes on disjoint queues — there is nothing to steal
- Low throughput, where an extra UDP protocol buys nothing
- You want the stock `queue.worker()` — it will not use the deque, so the mesh
  is pure overhead
- Scaling replicas is the actual goal; reach for
  <SdkLink to="modules/autoscaling">autoscaling</SdkLink> instead, since mesh
  moves work between running nodes rather than adding them

</SdkOnly>
