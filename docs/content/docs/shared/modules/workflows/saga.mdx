---
title: Sagas
description: "Roll back completed workflow steps in reverse order when a run fails — declare a compensator per step and flexiq handles the rest."
---

A saga is a workflow where steps that succeed register a **compensator** —
a task that undoes that step's side effect. If a later step fails, flexiq
automatically rolls back every already-completed step by running its
compensator, in reverse-dependency order, so the run ends in a consistent
state instead of a half-applied one. There's no separate "saga" API — any
DAG workflow becomes a saga the moment one of its steps declares a
compensator.

## Basic example

<CodeTabs>
  <Tab sdk="python">

```python
from flexiq import Queue
from flexiq.workflows import Workflow

queue = Queue()

@queue.task()
def unreserve_inventory(forward_args, forward_kwargs, forward_result):
    inventory_api.release(forward_result["order_id"])

@queue.task(compensates=unreserve_inventory)
def reserve_inventory(order_id: str) -> dict:
    inventory_api.reserve(order_id)
    return {"reserved": True, "order_id": order_id}

@queue.task()
def refund_payment(forward_args, forward_kwargs, forward_result):
    payment_api.refund(forward_result["charge_id"])

@queue.task(compensates=refund_payment)
def charge_payment(order_id: str) -> dict:
    return {"order_id": order_id, "charge_id": payment_api.charge(order_id)}

@queue.task()
def ship_order(order_id: str):
    raise RuntimeError("Warehouse offline")
# No compensator for ship — if it never succeeded, there's nothing to undo.

wf = Workflow(name="checkout")
wf.step("reserve", reserve_inventory, args=("4212",))
wf.step("charge", charge_payment, args=("4212",), after="reserve")
wf.step("ship", ship_order, args=("4212",), after="charge")

# A worker is already running elsewhere (queue.run_worker()).
run = queue.submit_workflow(wf)
status = run.wait()
# ship fails → charge rolled back (refund_payment) → reserve rolled back (unreserve_inventory)
# status.state is WorkflowState.COMPENSATED
```

        version: 1,
        dag_bytes: dag.to_json(|_| None)?.into_bytes(),
        step_metadata: HashMap::from([

            ("charge".into(), step("charge_payment", Some("refund_payment"))),
            ("ship".into(), step("ship_order", None)),
        ]),
        node_payloads: HashMap::from([
            ("reserve".into(), order.clone()),
            ("charge".into(), order.clone()),
            ("ship".into(), order),
        ]),
        queue_default: "default".into(),
        params_json: None,
        deferred_node_names: HashSet::new(),
        cache_hit_nodes: HashMap::new(),
        parent_run_id: None,
        parent_node_name: None,
        default_timeout_ms: 300_000,
        default_priority: 0,
        default_max_retries: 3,
        result_ttl_ms: None,
        namespace: None,

`submit_workflow` writes the definition, the run, a `WorkflowNode` per step,
and one job per step wired through `depends_on` — so the DAG runs in order on
an ordinary worker. **Nothing in Rust rolls it back.** `flexiq-workflows` is
the storage half of the engine: it has the `compensate` field, the
`Compensating` / `Compensated` / `CompensationFailed` states, and the three
setters that write them, but no tracker that notices a step failing and
decides what to undo. Submission reads only `task_name`, `queue`,
`max_retries`, `timeout_ms` and `priority` off a `StepMetadata`; `compensate`
is recorded and otherwise ignored. Driving rollback is yours: watch node
status through `WorkflowStorage::get_workflow_nodes` and enqueue the
compensators yourself.

## How it works

1. A step's forward execution fails with its retries exhausted.
2. flexiq collects every step that **completed** and declared a
   compensator — steps that are pending or skipped never ran, and a
   step that itself failed has nothing to undo, so all three are left
   alone.
3. Those steps are grouped into **reverse-topological waves** — the most
   downstream completed steps first, so a step is never rolled back before
   whatever depends on it. Compensators within one wave run in parallel;
   the next wave only starts once the current one fully drains.
4. Each compensator is enqueued idempotently (see [Idempotency](#idempotency))
   with the forward step's result available to it.
5. Once a wave finishes: if every compensator in it succeeded, the next
   wave starts. If any failed, rollback stops there — remaining steps are
   left un-rolled-back, since further undo may depend on the failed step's
   own undo — and the run ends `CompensationFailed` instead of
   `Compensated`.

### Watch a saga roll back

Fail a step and the completed ones undo in reverse-topological order. Steps

## Declaring compensators

Each step names a rollback task; when the run fails, flexiq calls it with
the forward step's outcome:

<CodeTabs>
  <Tab sdk="python">

```python

# task's args, kwargs, and return value.
@queue.task()
def refund_payment(forward_args: tuple, forward_kwargs: dict, forward_result: dict) -> None:
    payment_api.refund(forward_result["charge_id"])

@queue.task(compensates=refund_payment)
def charge_payment(order_id: str) -> dict:
    return {"order_id": order_id, "charge_id": payment_api.charge(order_id)}
```

StepMetadata {

that task: what a compensator is called with is decided by whatever enqueues
it, which here is your own code. A compensator is an ordinary
`#[flexiq::task]` function — give it the parameters you intend to pass.

### Decorator-level default

`@queue.task(compensates=…)` sets a task's default compensator wherever
it's used; `Workflow.step(…, compensates=…)` overrides it (or disables
compensation) for one specific step:

```python
wf.step("charge", charge_payment, compensates=refund_v2)  # override decorator default
wf.step("charge", charge_payment)                          # inherit decorator default
wf.step("charge", charge_payment, compensates=None)         # disable compensation
```

</Callout>

<SdkOnly sdk="rust">

Before reaching for `StepMetadata::compensate`, know that the field is inert:
nothing collects completed nodes, nothing builds waves, and nothing enqueues the
task it names. A saga that actually rolls back is written one of two ways.

**One task, durable steps.** The forward work and its undo live in the same
body, so the undo can see what the forward step returned. This is the shape to
reach for first:

```rust
#[flexiq::task]
fn checkout(order_id: String) -> flexiq::Outcome<()> {
    let mut step = flexiq::current_step();

    let hold = step.run_keyed("reserve", &order_id, || reserve(&order_id))?;
    let charge = step.run_keyed("charge", &order_id, || charge(&order_id))?;

    // A step that may need undoing commits its failure as a value.
    let shipped: Result<(), String> = step.run_keyed("ship", &order_id, || {
        Ok(ship(&order_id).map_err(|e| e.to_string()))
    })?;

    if let Err(reason) = shipped {
        // Reverse order, innermost first — the ordering waves would have given you.
        step.run_keyed("refund", &order_id, || refund(&charge))?;
        step.run_keyed("unreserve", &order_id, || unreserve(&hold))?;
        return Err(flexiq::TaskError::fatal(reason).into());
    }
    Ok(())
}
```

Memoization does the idempotency: a committed step is not re-run on a later
attempt, so a rollback interrupted halfway resumes rather than double-refunding.

<Callout type="warn" title="Keyed steps, not `run`">
  Every step on a compensating path must use `run_keyed`. An unkeyed step is
  matched **by position** in the recorded sequence, and the undo branch asks for
  steps the earlier attempt never recorded there — the run fails with a step
  divergence before any compensator body executes. A keyed step is matched by
  key wherever it sits, and one that was never recorded is simply new ground.
</Callout>

<Callout type="warn" title="The failing step must not abort">
  Note that `ship` returns its failure rather than raising it. A step body that
  returns `Err` commits nothing and leaves its own position outstanding, and the
  session refuses to start another step while one is — so the very next
  `run_keyed` fails with `started while step 'ship' is still uncommitted`,
  surfacing as a retryable error and a retry loop that never reaches the
  rollback.

  So: forward steps you will never compensate can use `?` freely. The one whose
  failure *triggers* the rollback has to hand the failure back as data, the way
  `Result<(), String>` does above.
</Callout>

**Separate jobs, driven by you.** If the rollback has to be its own job, the
node row has columns for it — `set_workflow_node_compensation_job` moves a node
to `Compensating` and records the job id, then
`set_workflow_node_compensated` or `set_workflow_node_compensation_failed`
closes it out. The reverse-topological ordering is yours to compute;
`topological_order` gives you the forward order to walk backwards.

</SdkOnly>

## Steps without compensators

A step that doesn't declare a compensator is skipped during rollback, and
so is a step that never ran because it was downstream of the step that
failed — only a **completed** step with a compensator is rolled back:

<CodeTabs>
  <Tab sdk="python">

```python
wf = Workflow(name="partial-saga")
wf.step("a", task_a, args=(1,), compensates=undo_a)  # rolled back if the run fails after a completes
wf.step("b", task_b, args=(2,), after="a")            # no compensator — left as-is
wf.step("c", task_c, args=(3,), after="b", compensates=undo_c)

# If b fails: only a is rolled back (b never completed; c never ran).
# If c fails: c has no completed result, so only a is rolled back.
```

  </Tab>
  <Tab sdk="node">

// If c fails: c has no result yet, so only a is rolled back.

<SdkOnly sdk="python">

<Callout type="info">
  These four are a subset of `WorkflowState`'s six terminal states —
  `is_terminal()` is also `True` for `CANCELLED` (compensation never runs
  on a cancelled run) and `COMPLETED_WITH_FAILURES`, covered next.
</Callout>

</SdkOnly>

<SdkOnly sdk="rust">

Read that table as a vocabulary, not a state machine that runs. Every one of
those four is a value you pass to `update_workflow_run_state` yourself; nothing
transitions a run on its own.

`WorkflowState` has ten variants in all — the four above plus `Pending`,
`Running`, `Paused`, `Compensating`, `Cancelled` and `CompletedWithFailures`.
What it also ships is the legal-move table, which is worth using even though the
writer does not:

```rust
use flexiq::workflows::WorkflowState;

assert!(WorkflowState::Running.can_transition_to(WorkflowState::Compensating));
assert!(WorkflowState::Compensating.can_transition_to(WorkflowState::Compensated));
// Terminal is terminal — nothing leaves Compensated.
assert!(!WorkflowState::Compensated.can_transition_to(WorkflowState::Running));
```

`update_workflow_run_state` does **not** call it. Gate on it before the write or
a retried handler will happily move a `Compensated` run back to `Running`. Note
which edges exist: `Compensating` is reachable from `Running`, `Completed`,
`CompletedWithFailures` and `Failed`, and `Cancelled` has no outgoing edge at
all — a cancelled run cannot be compensated, which matches the rule everywhere
else.

</SdkOnly>

## Compensating on continue-mode workflows

<SdkOnly sdk="python">

By default, `on_failure="continue"` workflows never trigger compensation —
they run every step regardless of individual failures and always reach
`COMPLETED_WITH_FAILURES` if any step failed. Opt in with
`compensate_on_continue=True`:

```python
wf = Workflow(
    name="resilient_checkout",
    on_failure="continue",
    compensate_on_continue=True,
)
wf.step("charge", charge_payment, args=("4212",))
wf.step("ship", ship_order, args=("4212",), after="charge")

run = queue.submit_workflow(wf)
```

With `compensate_on_continue=True`, once the run settles, a run with at
least one failed step transitions from `COMPLETED_WITH_FAILURES` into
`Compensating` — compensators for every *succeeded* step then run in
reverse-topological order, same as a `fail_fast` saga, and the run ends
`Compensated` or `CompensationFailed`. Without it, a `continue`-mode run
with failures just stays `COMPLETED_WITH_FAILURES` and no compensation
runs.

</SdkOnly>

<SdkOnly sdk="node">

<Callout type="info" title="Node: no continue-mode compensation">
  The Node builder has no run-level failure policy, so there is no
  `compensateOnContinue` equivalent. `on_failure` here is only a per-step
  `condition` (`"on_success"` | `"on_failure"` | `"always"`), not a
  continue-vs-abort mode for the whole run. Saga compensation is declared
  per step with `compensate` and runs only when the run itself fails.
</Callout>

</SdkOnly>

<SdkOnly sdk="java">

<SdkOnly sdk="rust">

<Callout type="info" title="No run-level failure policy to opt into">
  `SubmitStaticWorkflowRequest` carries no `on_failure` mode and no

  it is what your own code does when it sees a failed node.

  `CompletedWithFailures` is still a real state you can write, and
  `can_transition_to` allows `CompletedWithFailures → Compensating`, so the
  continue-then-compensate shape is expressible. It is just a sequence of
  writes, not a flag.
</Callout>

Inside a single durable-step task the distinction is which shape the step's
value takes:

```rust
// Fail fast — the abort ends the attempt here.
let charge = step.run_keyed("charge", &order_id, || charge(&order_id))?;

// Continue — the failure is committed as the step's value, so the body runs on.
let shipped: Result<(), String> = step.run_keyed("ship", &order_id, || {
    Ok(ship(&order_id).map_err(|e| e.to_string()))
})?;
```

Only the second one keeps going. `.is_ok()` on the first would not: an aborted
step commits nothing and leaves its position outstanding, so the next step in
that attempt is refused. Continue mode here means a step that *succeeds at
recording a failure*, which is also what makes the outcome survive a retry.

</SdkOnly>

## Idempotency

Every compensation job is enqueued with a deterministic idempotency key —
`compensation:{run_id}:{node_name}` — so a compensation that's
re-triggered (for example after a worker or tracker restart mid-rollback)
hits the existing dedup and becomes a no-op instead of running the
rollback twice.

That guarantee is at the *job* level, not the function body: a worker can
still retry a compensator on a transient failure before its own retries
are exhausted. Write compensator bodies to be safely re-runnable, the same
way you would any other task.

## Combining with conditions

Conditions and compensation compose. An `on_failure` step runs first as
the run settles toward failure; once the run is failed, compensation then
rolls back the completed compensable steps:

<CodeTabs>
  <Tab sdk="python">

```python
wf = Workflow(name="safe-checkout")
wf.step("reserve", reserve_inventory, args=("4212",), compensates=unreserve_inventory)
wf.step("charge", charge_payment, args=("4212",), after="reserve", compensates=refund_payment)
wf.step("ship", ship_order, args=("4212",), after="charge")
wf.step("notify_failure", send_failure_email, args=("4212",), after="ship", condition="on_failure")
```

`condition` is a step field, and like `compensate` it is an opaque string that
submission records but never evaluates:

```rust
StepMetadata {
    task_name: "send_failure_email".into(),
    condition: Some("on_failure".into()),
    ..Default::default()
}
```

`submit_workflow` pre-enqueues every non-deferred node up front and wires it
with `depends_on`, and a dependency counts as satisfied only once it reaches
`Complete` — so an `on_failure` step submitted this way waits forever behind
the step it was meant to react to. Branch on outcome the other way round: list
the node in `deferred_node_names` so it gets a `WorkflowNode` row and no job,
then enqueue it yourself once the run's node statuses tell you to.

## Events

<SdkOnly sdk="python">

Saga lifecycle emits dedicated events on the queue's event bus, subscribed
via `queue.on_event(event_type, callback)`:

| Event | Fires when |
|---|---|
| `WORKFLOW_COMPLETED_WITH_FAILURES` | A `continue`-mode run finished with at least one failure |
| `WORKFLOW_COMPENSATING` | The run enters the compensation phase |
| `WORKFLOW_COMPENSATED` | Every compensator succeeded |
| `WORKFLOW_COMPENSATION_FAILED` | At least one compensator failed |
| `NODE_COMPENSATING` | A step's compensator was enqueued |
| `NODE_COMPENSATED` | A step's compensator finished successfully |
| `NODE_COMPENSATION_FAILED` | A step's compensator failed after retries |

</SdkOnly>

<SdkOnly sdk="node">

<Callout type="info" title="Node: no saga events">
  The Node SDK emits only the four job-lifecycle events — `job.completed`,
  `job.retrying`, `job.dead`, `job.cancelled` — via `queue.on(...)`. There
  are no `WORKFLOW_COMPENSATING` / `NODE_COMPENSATED`-style saga events. Track
  compensation progress by polling the run handle: `handle.status()` and
  `handle.nodes()`.
</Callout>

</SdkOnly>

<SdkOnly sdk="java">

<Callout type="info" title="Java: no saga events">
  Java's `EventName` enum has only the four job outcomes — `SUCCESS`, `RETRY`,
  `DEAD`, `CANCELLED`. No workflow/saga transition events are emitted. Poll
  `WorkflowRun` / `status.nodes` for compensation progress.
</Callout>

</SdkOnly>

<SdkOnly sdk="rust">

There is no event bus — not for saga transitions and not for job outcomes.
`WorkerBuilder` exposes no hook at all; `flexiq_core::Worker::on_outcome` is the
nearest seam and the builder does not reach it.

For a saga written as durable steps this matters less than it looks, because the
rollback is a branch in code you wrote — put the notification on the branch:

```rust
if let Err(reason) = shipped {
    notify_rollback(&order_id, &reason);   // your own transport
    step.run_keyed("refund", &order_id, || refund(&charge))?;
}
```

Send it outside the step closures, not inside one. A step body is memoized: on a
replay it does not run, so a notification in there fires once for the first
attempt and never again — which is right for a charge and wrong for an alert.

For a saga spread over workflow nodes, the compensation columns are the record
to poll: `get_workflow_nodes(run_id)` and look at `status`,
`compensation_started_at`, `compensation_completed_at` and `compensation_error`.
`WorkflowNodeStatus::{Compensating, Compensated, CompensationFailed}` are the
three to watch, and `CompensationFailed` is the one that wants a human.

</SdkOnly>
