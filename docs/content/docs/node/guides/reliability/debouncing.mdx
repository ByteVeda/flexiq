---
title: Debouncing
description: "Collapse a burst of enqueues into one run on a sliding deadline."
---

Debouncing collapses repeated enqueues that share a key into a **single** job
whose run keeps sliding into the future while the calls keep coming. It is the
answer to "rebuild this user's report once they stop editing", not "run this at
most 100 times a minute".

```ts
queue.task("buildReport", buildReport, {
  debounce: "5m", // slide the run 5 minutes out on every enqueue
  debounceKey: "report:{userId}", // one window per user
  debounceMaxWait: "30m", // but never delay past 30 minutes
});

queue.enqueue("buildReport", [{ userId: "u1" }]); // creates the job
queue.enqueue("buildReport", [{ userId: "u1" }]); // same job id — deadline moves
```

Each enqueue returns the **existing** job's id, so a burst of a hundred calls
leaves one pending row. The deadline is `min(now + debounce, firstSeen +
debounceMaxWait)`, recomputed inside the same storage transaction that finds
the open window — two producers racing on one key cannot both create a job.

## Durations

`debounce` and `debounceMaxWait` take milliseconds as a number, or a suffixed
string — `"500ms"`, `"30s"`, `"5m"`, `"2h"`, `"1d"`.

## The key is the window

`debounceKey` is a template resolved against the call's arguments:

- `{userId}` reads that property off the first object argument carrying it.
- `{0}`, `{1}`, … read an argument by position.

```ts
queue.task("syncUser", syncUser, {
  debounce: "10s",
  debounceKey: "sync:{0}", // syncUser(userId: string)
  debounceMaxWait: "2m",
});
```

A placeholder that resolves to nothing — a missing property, an out-of-range
position, an object where a scalar was expected — **throws at enqueue**. The
alternative would be one global window silently shared by every caller, which
is the failure debouncing exists to avoid. A template with no placeholder at
all is legal and means exactly that: one window for the whole task.

## Max wait is mandatory

`debounce` without `debounceMaxWait` throws when the task is registered.
Without a ceiling, a caller who never stops enqueuing starves the job forever —
the classic debounce footgun. The ceiling is measured from when the window
opened, not from the latest call, so the job runs on schedule no matter how
long the burst lasts.

## Which payload runs

By default the job runs with the arguments the window **opened** with; later
enqueues move the deadline and nothing else. Set `debounceReplacePayload` to
run with the newest arguments instead:

```ts
queue.task("buildReport", buildReport, {
  debounce: "5m",
  debounceKey: "report:{userId}",
  debounceMaxWait: "30m",
  debounceReplacePayload: true,
});
```

Priority, metadata, notes and dependencies always belong to the job that opened
the window — only the deadline and (optionally) the payload move.

## Per-enqueue debouncing

The same fields work on `enqueue`, so a producer that registers no handler can
still debounce, and a single call can override the task's defaults field by
field:

```ts
queue.enqueue("buildReport", [{ userId: "u1" }], {
  debounce: "30s",
  debounceKey: "report:{userId}",
  debounceMaxWait: "5m",
});
```

## Limits

- `uniqueKey` and `debounce` cannot be combined — they are two different
  collapse rules. `uniqueKey` pins the first job in place; debounce moves it.
  See [Idempotency](/node/guides/reliability/idempotency) for the dedup path.
- `enqueueMany` cannot debounce. A batch is a single storage call with no
  window to slide; enqueue debounced jobs one at a time.
- Subscribers cannot debounce. A publish is fanned out by the core, one
  delivery per subscription, and never passes through the enqueue path.
- `delayMs` has no effect on a debounced enqueue, and neither does an enqueue
  gate's `defer`. The window owns the schedule: the deadline is recomputed from
  `debounce` and `debounceMaxWait` inside the storage transaction, so any delay
  the caller asked for is overwritten.

<Callout type="info">
  Debouncing collapses *enqueues*; to bound how fast the jobs you do create
  dispatch, use [rate limiting](/node/guides/reliability/rate-limiting).
</Callout>
