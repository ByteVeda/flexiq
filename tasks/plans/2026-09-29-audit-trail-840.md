# Audit trail for token-authorised calls (#840)

## Goal

Answer, after the fact: *which token enqueued this job*, *who cancelled it*,
*what did the token we just revoked do while it was valid*.

One record per authorised mutating call on the gRPC doors (native and the
`/v1` JSON facade — same layer stack): token id, principal name, namespace,
operation, target, timestamp, outcome. **Never the token or its digest.**

## Decisions

### 1. Where it lands: a storage table (`audit_log`)

A log stream answers nothing retroactively unless the operator shipped logs
before the day they needed them; the issue's whole point is that nobody knows
in advance. The table is on by default wherever a token door is on, survives a
pod restart and is queryable by token and by target.

Cost accepted: three-backend parity (migration `m0022`, SQLite/PG through a
`diesel_common` macro, Redis by hand) and a retention obligation (§3).

**Off the request path.** The door never waits on the audit write: records go
into a bounded channel (4096) drained by one writer task that appends in
batches (≤ 256 per `spawn_blocking` call). If the channel is full or the append
fails, the record is written as a `warn!` line under log target
`flexiq::audit` and `flexiq_audit_records_dropped_total` increments — degraded
to the log stream, never dropped silently. Refusing the RPC when the audit
write fails would make the audit table an availability dependency of enqueue;
not taking that.

### 2. Writes only

Audited: every call whose gate requirement is a **write scope** — `produce`
(non-read producer methods) and `admin` (non-inspect admin methods). Derived
from the existing `gate` tables, so a new mutating RPC is audited by default
(fail closed, same as the scope default).

Not audited:
- `read` / `inspect` methods — volume is dominated by polling (`GetJob`,
  `WatchJobs`) and the record is noise. Follow-up if "what did it see" is
  asked for.
- The executor door (`execute`): that is workers' own traffic, high volume, and
  its effects are already recorded as job state transitions.
- Unauthenticated calls: no trusted token id exists. `TokenStore` already logs
  those refusals.

Denials **are** recorded: a valid token refused `PERMISSION_DENIED` on a write
method (gate scope refusal or a narrowed grant) is exactly what an audit wants.

### 3. Retention: server-owned window, default 90 days

`FLEXIQ_GRPC_AUDIT_RETENTION_DAYS` (default `90`, `≥ 1`; Helm
`grpc.auditRetentionDays`) — `FLEXIQ_GRPC_` because every other knob of this
listener carries that prefix. The server prunes its own
namespace hourly with `purge_audit(namespace, cutoff)`. The DELETE is
idempotent, so replicas need no election.

Not folded into core `RetentionConfig`: that struct is a per-queue shell
setting with dashboard surfaces in three SDKs; audit is a server concern and
the shells never write it.

### 4. Attribution column on `jobs`: not in this change

With `audit_log` indexed on `(namespace, target_kind, target)`, "which token
enqueued job X" is one indexed point query (`fq audit list --job X`). The column
would cost ~40 literal sites + a migration and duplicate that answer. Left as a
separate decision.

## Record

```
audit_log
  id           TEXT PK         uuid v7
  namespace    TEXT NOT NULL
  at_ms        BIGINT NOT NULL
  token_id     TEXT NOT NULL   public id (fqt_<id>.… prefix part only)
  principal    TEXT NOT NULL   token name at call time
  operation    TEXT NOT NULL   "flexiq.producer.v1.Producer/Enqueue"
  target_kind  TEXT NULL       job | workflow_run | queue | dead_letter | worker | periodic | task
  target       TEXT NULL
  outcome      TEXT NOT NULL   gRPC code name: OK, PERMISSION_DENIED, …
indexes: (namespace, at_ms), (namespace, token_id, at_ms), (namespace, target_kind, target)
```

A call with several targets (`EnqueueBatch`, one per job) writes one record per
target; a call refused before its target is known writes one record with no
target. `ReplayDeadLetter` and `TriggerPeriodicTask` name both their subject
and the job they made, so "who enqueued job X" covers replayed and triggered
jobs too.

## Mechanism

- **`Principal` gains `name`** — `TokenStore::authenticate` already holds the
  row; no extra read.
- **`AuditLayer`** sits *outside* `AuthLayer` (inside `MetricsLayer`) so it
  sees gate refusals. It inserts an `AuditContext` slot into the request
  extensions; `AuthLayer` fills the principal + door scope, handlers push
  targets (`audit::target(&request, Kind::Job, &id)`). After the response the
  layer reads the outcome with the same `answered_code` logic `MetricsLayer`
  uses (shared, not copied), the operation via `metrics::labels`, and sends the
  records to the sink. All audited methods are unary, so the streaming
  trailers blind spot does not apply.
- **Handlers that set targets**: producer `Enqueue`, `EnqueueBatch`,
  `CancelJob`, `SubmitWorkflow`; admin queues, dead letters, workers, periodic,
  overrides.

## Core storage

- `records.rs`: `AuditRecord`, `AuditFilter { token_id, target: Option<(kind,
  id)>, since_ms, until_ms }`, keyset page on `(at_ms, id)` descending
  (existing `cursor.rs`). Re-exported at the crate root.
- `Storage`: `append_audit(&[AuditRecord])`, `list_audit(namespace, &filter,
  limit, cursor)`, `purge_audit(namespace, older_than_ms)`. No defaults.
- Contract tests in the shared storage suite (runs on all three in CI).

## Read surface

- Admin RPC `ListAuditRecords` (`no_side_effects` → `inspect` scope), facade
  `GET /v1/admin/audit`. Proto change → regenerate Go `internal/pb` and OpenAPI.
- `fq audit list [--token-id ID] [--job ID | --target KIND:ID | --kind KIND]
  [--since …] [--until …] [--page-size N] [--page-token T | --all]`. `--token-id`,
  not `--token`: the flag names a public id, and `fq`'s credential is
  `FLEXIQ_TOKEN`.

## Tests

- Core: append/list by token, by target, time range, pagination, purge scoped
  to namespace.
- Server wire (`tests/`): enqueue writes token id + name + job id + `OK`;
  a read-scoped token calling `Enqueue` writes `PERMISSION_DENIED`;
  `GetJob` writes nothing; `EnqueueBatch` writes N; facade enqueue writes the
  same record; no record field contains the secret; sink overflow falls back to
  the log and counts.
- `fq audit list` against a real server.
